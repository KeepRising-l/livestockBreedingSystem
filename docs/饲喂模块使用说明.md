## 一、模块定位

饲喂模块负责养殖场日常饲喂的全流程管理，是后续成本核算的基础数据来源。包含两个子功能：

1. **饲喂方案**：场主配置「不同畜种+不同生长阶段」的标准投喂方案（每只每次投喂多少精料/青贮/干草，单价多少）
2. **饲喂记录**：员工每天提交投喂记录，自动进入「待审核」状态，场主审核通过后才算有效数据

## 三、饲喂方案怎么用

### 3.1 操作路径

侧边栏 → 饲喂管理 → 饲喂方案

### 3.2 核心字段说明

| 字段 | 说明 | 示例 |
| --- | --- | --- |
| 方案名称 | 同一养殖场内唯一 | 育肥牛标准方案 |
| 适用畜种 | cattle / sheep / pig | cattle |
| 适用生长阶段 | 与档案的生长阶段对应 | 育肥期 / 保育期 / 犊牛期 |
| 适用圈舍类型 | A/B/C/D，可不填（不限） | B |
| 每日投喂次数 | 1-10 | 2（早晚各一次） |
| 精料/青贮/干草 重量 | kg/只·次 | 3.0 / 6.0 / 1.5 |
| 精料/青贮/干草 单价 | 元/吨 | 3200 / 600 / 1200 |
| **预计日成本** | **系统自动计算，不可编辑** | 30.0 元/只·天 |

### 3.3 预计日成本计算公式

```
预计日成本 = Σ(每次重量 × 每日次数 × 单价 ÷ 1000)

例：精料 3kg × 2次 × 3200元/吨 ÷ 1000 = 19.2 元
   青贮 6kg × 2次 × 600元/吨 ÷ 1000 = 7.2 元
   干草 1.5kg × 2次 × 1200元/吨 ÷ 1000 = 3.6 元
   合计 = 30.0 元/只·天
```

### 3.4 操作权限

- 新增/编辑/删除：**仅场主和超管**
- 查看列表/详情：所有登录用户

### 3.5 删除限制

方案被任何饲喂记录引用时不能删除（避免历史记录失去方案上下文）。需要先删除引用此方案的所有饲喂记录才能删方案。

## 四、饲喂记录怎么用

### 4.1 操作路径

侧边栏 → 饲喂管理 → 饲喂记录

### 4.2 提交记录流程

```
员工点击「提交饲喂记录」
    ↓
填写：日期 + 时段(早/晚) + 圈舍 + 实际投喂重量 + 饲喂头数
    ↓（可选）选择关联的饲喂方案
    ↓
系统自动：
  - 校验同日同时段同圈舍不能重复
  - 从所选方案带出 plan_xxx（计划重量）字段
  - 按实际重量 × 方案单价 自动算 feed_cost（本次饲喂成本）
  - audit_status 强制为「待审核」
    ↓
场主在列表页点「通过」或「驳回」
    ↓
通过后：status 自动置为「已投喂」，feed_time 记录时间，不可再改/删
驳回后：员工可修改后重新提交（修改时 audit_status 重置为「待审核」）
```

### 4.3 饲喂成本计算公式

```
本次成本 = Σ(实际重量 × 方案对应单价 ÷ 1000)

例：实际投喂精料 36kg × 3200元/吨 ÷ 1000 = 115.2 元
   实际投喂青贮 72kg × 600元/吨 ÷ 1000 = 43.2 元
   实际投喂干草 18kg × 1200元/吨 ÷ 1000 = 21.6 元
   合计 = 180.0 元
```

**注意**：成本是用「实际重量」算的，不是用方案里的「计划重量」。如果不选方案，则没有单价数据，feed_cost 为空。

### 4.4 状态字段含义

饲喂记录有两个状态字段：

| 字段 | 取值 | 含义 |
| --- | --- | --- |
| `status`（投喂状态） | 未投喂 / 已投喂 / 已跳过 | 员工标记本次有没有真的投喂 |
| `audit_status`（审核状态） | 待审核 / 通过 / 驳回 | 场主审批结果 |

### 4.5 操作权限矩阵

| 操作 | 场主 | 员工 | 备注 |
| --- | --- | --- | --- |
| 查看列表 | ✅ | ✅ | 只能看自己养殖场的数据 |
| 提交记录 | ✅ | ✅ | 提交后自动进「待审核」 |
| 修改记录 | ✅ | ✅ | 只能改「待审核」状态的，改完还是「待审核」 |
| 删除记录 | ✅ | ✅ | 不能删「已通过」的 |
| 审核通过 | ✅ | ❌ | 仅场主/超管 |
| 审核驳回 | ✅ | ❌ | 仅场主/超管 |

## 五、典型使用场景

### 场景 1：员工早班投喂

1. 饲喂员 `feeder01` 登录系统
2. 进入「饲喂记录」页面
3. 点「提交饲喂记录」
4. 选日期=今天，时段=早，圈舍=B01
5. 选关联方案=「育肥牛标准方案」（系统会提示计划重量）
6. 填实际投喂精料 36kg、青贮 72kg、干草 18kg
7. 饲喂头数填 12（B01 圈里 12 头牛）
8. 投喂状态选「已投喂」
9. 点保存 → 系统提示「提交成功，等待审核」

此时记录状态 = `待审核`，成本 = `180 元`。

### 场景 2：场主审核

1. 场主 `sunshine` 登录系统
2. 进入「饲喂记录」页面
3. 在「审核状态」筛选 `待审核`
4. 看到饲喂员提交的记录
5. 点「通过」按钮（可填审核备注）
6. 系统提示「已通过」，记录状态变为 `通过`，投喂状态自动置为 `已投喂`

### 场景 3：场主驳回并要求重做

1. 场主发现某条记录的实际投喂量明显偏低（比如精料只投了 10kg，方案是 36kg）
2. 点「驳回」按钮，备注「投喂量与方案差距过大，请核实」
3. 饲喂员登录后看到记录状态 = `驳回`
4. 饲喂员点「编辑」，改成正确的数量，保存
5. 记录状态自动重置为 `待审核`，等场主再次审核

### 场景 4：配置新的饲喂方案

场主新进了一批羔羊，想配置专门的饲喂方案：

1. 进入「饲喂方案」页面
2. 点「新增方案」
3. 方案名称=`羔羊保育方案V1`
4. 适用畜种=`cattle`，适用阶段=`犊牛期`，适用圈舍=`A`
5. 每日投喂次数=3（羔羊少量多餐）
6. 精料 1.0kg、青贮 2.0kg、干草 0.5kg
7. 单价 3800 / 700 / 1500
8. 系统自动算出预计日成本 = `17.85 元/只·天`
9. 保存

之后员工提交饲喂记录时，可以选这个方案，系统会带出计划重量做参考。

## 七、常见问题

### Q1：超管登录后访问饲喂模块报「当前用户未关联养殖场」

**原因**：超管本身没有 farm_id，需要通过请求头 `X-Farm-Id` 指定要操作的养殖场。

**解决**：前端已自动处理（[request.ts](file:///d:/Code/system/livestock-web/src/api/request.ts#L14-L22) 会从 localStorage 读 `selectedFarmId` 加到请求头）。登录超管后等 1-2 秒等养殖场列表加载完，右上角切换到目标养殖场即可。

### Q2：耳标为什么是 4 位数字？前 2 位怎么来的？

耳标格式：**前 2 位 = 圈舍 ID 后 2 位** + **后 2 位 = 圈舍内顺序号**。

例：圈舍 ID=3（B01）里的第 1 头牛 → 耳标 `0301`，第 2 头 → `0302`。

设计原则：
- 前 2 位用圈舍 ID 保证全局唯一（避免 A01/B01/C01 这种字母不同数字相同的圈舍编号冲突）
- 后 2 位是圈舍内顺序号，畜禽出栏/死亡后耳标号会释放，可被复用

### Q3：为什么提交饲喂记录后状态是「待审核」而不是直接生效？

这是设计上的审核流程，目的是防止员工误操作直接污染成本数据。所有员工提交的饲喂记录都必须经场主审核通过后，才算正式有效数据（用于后续成本核算）。

如果你不想要这个流程，可以改 [feeding_service.py#L192](file:///d:/Code/system/livestock_server/app/services/feeding_service.py#L192) 里 `audit_status="待审核"` 改成 `audit_status="通过"`，并同步去掉 `_check_owner` 在审核接口的拦截。但**不建议**这样做，审核流程对养殖场管理是有价值的。

### Q4：饲喂成本是怎么算的？为什么要选方案？

饲喂成本 = 实际投喂重量 × 方案里配置的单价 ÷ 1000（吨转 kg）。

**必须选方案**才能算出成本，因为方案里存了单价。如果不选方案，系统只知道投喂了多少 kg，但不知道这些饲料值多少钱，feed_cost 字段就是空的。

### Q5：批量入栏的耳标为什么是连号的？

批量入栏时，系统会按圈舍顺序依次分配耳标。例：4 头牛都进 B01 圈舍（ID=3），耳标就是 `0302 / 0303 / 0304 / 0305`（0301 已经被之前的个体入栏用掉了）。

### Q6：MySQL 模式下重跑脚本会怎样？

脚本会先 `DELETE FROM` 清空所有业务表（保留表结构和超管账号），然后重新造数据。所以重跑不会出现耳标冲突、用户名重复等问题。
