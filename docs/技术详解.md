## 第 0 章：开工前的三件事

### 0.1 什么是"前后端分离"

**一句话**：这个项目分成两个独立程序 —— 一个负责"给人看的界面"，一个负责"跟数据打交道"，它们通过网络对话。

| | 前端 | 后端 |
|---|---|---|
| 目录 | `livestock-web/` | `livestock_server/` |
| 技术 | Vue 3 + TypeScript + Element Plus | Python + FastAPI + SQLAlchemy |
| 跑在哪 | 浏览器里 | 服务器上（本机就是 `127.0.0.1:8000`） |
| 端口 | 5173（开发时） | 8000 |
| 职责 | 展示数据、收集用户操作 | 校验规则、读写数据库、返回结果 |

**为什么要拆开**：
- 前端界面改起来快，改完刷新就看到效果（模块级热重载）
- 后端负责的规则（比如"妊娠状态不能重复配种"）不会被前端绕过
- 两边可以分别部署 —— 前端静态文件放 Nginx，后端跑在服务器

**代价**：多了一层"数据要跨网络传输"的环节，所以需要处理跨域、鉴权、加解密。这就是第 1 章和 5.2 节要解决的问题。

## 第 1 章：账号与安全

### 1.1 密码为什么存哈希，不存明文

**一句话**：数据库里不存 `123456`，存的是一串"密码经过单向搅碎机后的渣"。

**技术**：bcrypt（`livestock_server/app/core/security.py`）

**解决了什么问题**：
假设数据库被拖库了（很多真实事故都这样）。如果存明文，所有用户的密码直接暴露，攻击者拿去撞其他网站。存哈希则毫无用处 —— 因为 bcrypt 是**单向**的，算不出原文。

**它怎么工作**：

```python
def hash_password(password: str) -> str:
    pwd_bytes = password.encode("utf-8")[:72]   # bcrypt 有 72 字节上限，超长会报错，统一截断
    salt = bcrypt.gensalt()                     # 自动生成随机盐
    return bcrypt.hashpw(pwd_bytes, salt).decode("utf-8")
```

**关键细节：盐（salt）**
每次生成盐都不一样，所以**同一个密码 `123456` 存两次，数据库里两串哈希完全不同**。
作用是防止"彩虹表攻击" —— 攻击者无法预先算好所有常见密码的哈希值来批量比对。

**校验时怎么比对**：
```python
def verify_password(plain: str, hashed: str) -> bool:
    return bcrypt.checkpw(plain.encode()[:72], hashed.encode())
```
`checkpw` 内部会用哈希里带的盐重新计算一次，再比对结果。

**没它会怎样**：明文存密码是行业禁令，代码审查和安全扫描都会直接判不通过。

### 1.2 JWT：一张自己会过期的门票

**一句话**：JWT 就是一张**数字门票**，证明"你已经登录过了"，而且票上写了有效期。

**技术**：`python-jose` 库的 HS256 算法（`livestock_server/app/core/security.py`）

**解决了什么问题**：

**老做法**：服务端存一份 session，浏览器每次请求都带一个 session id，服务端拿 id 查表确认登录。
→ 问题：每个请求都要查一次数据库，高并发时数据库被大量重复查询拖垮。

**JWT 做法**：登录时服务端**用密钥签名**生成一串字符串，里面装着用户 ID 和过期时间。客户端拿着它，服务端**只验签名、不查库**就能确认身份。

**怎么跑的**：

```
① 登录成功后 —— 后端签发
   create_access_token(user_id, {"user_type": 2, "farm_id": 4})
   → 得到一串 "eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOjEsImV4cCI6..." 这样的字符串
   → 载荷里装了：用户ID、过期时间、以及签名用的密钥指纹

② 浏览器保存
   前端存进 localStorage（livestock-web/src/utils/token.ts）

③ 之后每次请求 —— axios 拦截器自动携带（livestock-web/src/api/request.ts）
   config.headers.Authorization = `Bearer ${token}`

④ 后端校验 —— get_current_user（livestock_server/app/core/deps.py）
   取出 Authorization 头 → decode_access_token() 验签 → 拿到 user_id → 查一次用户
```

注意第 ④ 步：**JWT 省掉的是"每次都查 session 表"，但仍然要查一次用户表** —— 因为还要拿到用户的实时状态（比如账号有没有被禁用）。

**没它会怎样**：每个请求都查 session 表，数据库压力大；而且前端要额外维护 session 机制。

**⚠️ 小白最容易搞错的一点**：
JWT 是**签名，不是加密**。里面的内容（用户 ID、农场 ID）任何拿到 token 的人都能解开看（Base64 解码即可）。防篡改靠的是签名，密钥只在服务端。
→ **结论：token 里绝不能放密码等敏感信息。**

### 1.3 权限的三道关卡

**一句话**：光隐藏菜单是不够的 —— 系统在三个地方各设一道关，层层拦截。

**这是新手最容易忽略的设计**：很多系统只在左侧菜单里把功能藏起来，用户看不到就以为安全了。但会写代码的人可以直接调接口绕过菜单。本项目做了三层：

| 关卡 | 在哪 | 拦什么 |
|---|---|---|
| **第 1 关：菜单不显示** | `Sidebar.vue` 的 `modulesOf()` 函数 | 看不到入口 |
| **第 2 关：路由拦截** | `router/index.ts` 的 `authGuard()` | 直接敲网址也进不去 |
| **第 3 关：后端鉴权** | 各模块 `api.py` 的路由依赖 | 绕过前端直接调接口也拿不到数据 |

**第 2 关怎么工作**（`livestock-web/src/router/index.ts`）：

```typescript
// 每次路由跳转前都会执行
export async function authGuard(to) {
  const token = getToken()
  if (!token) return '/login'                                    // 没登录 → 踢回登录页

  // 畜种校验：URL 里的 :species 必须属于当前养殖场可选的畜种
  const sp = to.params.species as string
  if (auth.livestockTypes.length > 0 && !auth.speciesRouteList.includes(sp)) {
    return '/404'                                                // 越权访问畜种 → 404
  }

  // 员工权限：路径第二段（模块名）必须在角色的权限清单里
  if (auth.userType === 3 && to.meta.auth !== false && to.path !== '/dashboard') {
    const perm = to.path.replace(/^\//,'').split('/')[1] || segments[0]
    if (!auth.perms.includes(perm)) return '/403'                // 没权限 → 403
  }
}
```

**关键设计**：判断"要访问哪个模块"的方式很朴素 —— **直接取 URL 路径的第二段当模块名**。
比如 `/cattle/feeding/plan`，第二段 `feeding` 就是模块名，跟后端约定的模块 key 一致。前后端用同一套字符串对齐，省去了配置表。

**⚠️ 注意**：`authGuard` 结尾有个 `try/catch` 会放行所有异常：
```typescript
} catch {
  // 权限校验异常时放行，由页面接口自行拦截（后端有真鉴权兜底）
}
```
这是**刻意的设计** —— 前端校验只是体验优化，不能因为它出问题就卡住用户。真正兜底的是第 3 关。

**没它会怎样**：员工知道 `/cattle/finance/sale` 这个地址，直接在地址栏敲进去就能看到全场的销售数据。

### 1.4 RBAC：角色决定你能碰哪些模块

**一句话**：给角色起个名字（饲喂员/兽医/繁育员），每个角色配一份"能碰哪些模块"的清单。

**技术**：角色-权限模型 + FastAPI 依赖注入（`livestock_server/app/core/perms.py`）

**数据是怎么存的**：

```
sys_user（用户）
   │  多对多
   ▼
sys_user_role（用户↔角色关联表）──► sys_role（角色）
                                        │
                                        │ perms 字段（JSON 数组）
                                        ▼
                            ["feeding","health"]  ← 员工能碰的模块
```

**后端怎么用这个清单**（`core/perms.py`）：

```python
def require_perms(perm: str):
    """校验当前用户是否拥有某模块权限"""
    def dependency(current_user = Depends(get_current_user),
                   db = Depends(get_db)):
        perms = get_user_perms(db, current_user.id)   # 查出该用户的权限集合
        if perm not in perms:
            raise BizException("无权限访问该模块", code=40303)
    return dependency
```

`require_perms("feeding")` 返回一个"检查函数"，交给 FastAPI 的依赖注入机制。

**用起来是这样的**（以圈舍模块为例，`modules/pen/api.py`）：

```python
router = APIRouter(dependencies=[Depends(require_perms("pen"))])
#              ↑ 整个圈舍模块的所有接口，都自动要求 pen 权限
```

**这一行的价值**：写在 router 上，等于给这个文件里**所有接口**批量加上了权限校验。新增接口时不会忘记加 —— 漏不掉。

**三种权限校验的分工**：

| 方式 | 用在哪 | 语义 |
|---|---|---|
| `require_perms("模块名")` | 6 个业务模块（pen/animal/feeding/health/inventory/breeding） | 员工按角色查模块权限 |
| `_require_admin(current_user)` | system 模块（31 处） | 只有超管能碰 |
| `Depends(get_current_user)` | 登录即可 | 只校验"是否登录" |

超管和场主的权限是**写死的、不看角色表**（`get_user_perms` 里：`user_type == 1` 直接返回全部模块，`== 2` 返回除 system 外的全部）。

**⚠️ 有 4 个模块没挂 `require_perms`** —— 详见 [第 7 章 技术债](#第-7-章-已知技术债与可改进点)。

### 1.5 多租户：养殖场之间的隔离墙

**一句话**：这个系统可以给很多家养殖场用，A 场的数据 B 场绝对看不到。

**技术**：所有查询强制带 `farm_id` 条件

**怎么做的**：

用户表里有个 `farm_id` 字段，记录"这个人属于哪个养殖场"。所有业务查询都加一句：

```python
db.query(Pen).filter(Pen.farm_id == current_user.farm_id)
```

**难点在于"忘记加"**：如果某个新接口忘了写这一句，A 场老板就能看到 B 场的圈舍。

**本项目的处理**：
- 前端每次请求都带 token，后端从 token 解析出用户 → 拿到 `farm_id`
- 业务代码统一用 `current_user.farm_id`，不从前端传参接收（**前端传的 farm_id 一律不信**）

**验证方法**：拿 A 场的账号手动改请求参数去查 B 场的圈舍列表，应该返回空。

### 1.6 超管切换养殖场的一个小技巧

**场景**：超管不属于任何养殖场，但要在多个养殖场之间切换视角看数据。实现上有个难点：所有业务代码都写死了 `current_user.farm_id`，怎么让超管能"临时"变成某个养殖场的人？

**如果直接赋值会出事**：
```python
user.farm_id = x_farm_id    # ❌ 这样写会污染数据库会话
```

SQLAlchemy 会把 `user` 当成"被修改过的持久化对象"，请求结束时如果会话被提交，**这个临时值就会被写进数据库** —— 超管的 farm_id 就被改坏了。

**本项目的解法**（`livestock_server/app/core/deps.py`）：

```python
if user.user_type == 1 and x_farm_id and x_farm_id > 0:
    # 用 object.__setattr__ 绕过 SQLAlchemy 属性机制，避免污染 session dirty
    object.__setattr__(user, "farm_id", x_farm_id)
```

**`object.__setattr__` 是什么**：Python 内置方法，直接操作对象的 `__dict__`（属性字典），**跳过 SQLAlchemy 挂在属性上的追踪机制**。

`object.__setattr__`  = "偷偷改一下内存里的值，不惊动任何监控器"

| 写法 | 效果 |
|---|---|
| `user.farm_id = 5` | 调用 SQLAlchemy 拦截器 → 标记为"已修改" → 可能被写库 |
| `object.__setattr__(user, "farm_id", 5)` | 直接改内存值 → SQLAlchemy 完全不知情 → 不会被写库 |

请求结束时 `db.close()` 会丢弃整个会话，这个临时值随之消失，数据库里的 `farm_id` 保持原样。

**还有一个配套的前端设计**（`livestock-web/src/api/request.ts`）：

```typescript
const payload = JSON.parse(atob(token.split('.')[1]))   // 前端也能解 JWT
if (payload.user_type === 1) {                        // 只有超管才带这个头
  config.headers['X-Farm-Id'] = String(getSelectedFarmId())
}
```

前端从 token 里解出 `user_type`，**只有超管**才附加 `X-Farm-Id` 请求头。后端再校验一遍 `user_type == 1` —— 双保险。

**没它会怎样**：要么超管看不到任何数据（每个请求 farm_id 为空），要么普通用户能伪造请求头越权查看别的养殖场。

## 第 2 章：页面的数据从哪来

### 2.1 菜单是怎么"长"出来的

**一句话**：菜单不是写死在页面里的 HTML，而是**根据"你是谁 + 你有哪些权限"算出来的**。

**代码在哪**：`livestock-web/src/layouts/components/Sidebar.vue`

**数据来源有两层**：

**第一层：模块清单（写死的配置）**
```typescript
const MODULES = [
  { key: 'feeding', title: '饲喂管理', icon: 'Food', roles: [1,2,3], pages: [...] },
  { key: 'review',  title: '审核中心', icon: 'Stamp', roles: [1,2],   pages: [...] },
  // ...
]
```

每个模块带两个关键属性：
- `roles`：哪些角色能看（`[1,2,3]` = 超管/场主/员工；`[1,2]` = 只有超管和场主）
- `pages`：这个模块下有哪几个页面

**第二层：当前用户（运行时算）**
```typescript
function modulesOf(sp: string): ModuleDef[] {
  return MODULES.filter(mod => {
    if (!mod.roles.includes(userType.value)) return false          // 角色不匹配 → 隐藏
    if (userType.value === 3 && !authStore.hasPerm(mod.key)) return false  // 员工还要看角色权限清单
    return true
  })
}
```

**三层结构**渲染成这样的菜单：

```
我的养殖场（el-sub-menu）
  └─ 牛场（el-sub-menu，按畜种）
       ├─ 圈舍管理（el-sub-menu，模块）
       │    └─ 圈舍列表（el-menu-item，页面）
       ├─ 饲喂管理
       │    ├─ 饲喂方案
       │    └─ 饲喂记录
       └─ ...
```

**为什么要分畜种再分模块**：
一个养殖场可能同时养牛羊猪（数据库里 `farm_info.livestock_types = "牛,羊,猪"`），三套数据必须分开统计。如果所有畜种的菜单平铺，会有几十个入口，用户根本找不到。

**⚠️ 代价（今天实测过的）**：三畜种场景下，侧边栏会渲染约 124 个菜单组件，展开动画会卡。

**没它会怎样**：所有人看到一模一样的菜单，员工能看到"审核中心"和"利润核算"，但点进去报 403 —— 体验很差。

### 2.2 列表页三件套：分页、筛选、条件复用

**现象**：系统里每个列表页（圈舍、档案、物资、订单…）长得都差不多，都有"搜索框 + 筛选下拉 + 分页器 + 表格"，这背后有没有共用的东西？

**有**：`livestock-web/src/composables/usePagedList.ts`（组合式函数）

**用了 Vue 的组合式 API**（Composition API）：把"列表页的通用逻辑"抽成一个可复用的函数，各页面调用它并传入自己的差异部分。

**典型用法（概念示意）**：

```typescript
const list = usePagedList({
  fetchApi: getPenListApi,        // 用哪个接口取数据
  defaultParams: { penType: 'A' }, // 默认筛选条件
})
// 之后 list.query() / list.reset() / list.pageNum 都可以直接用
```

**为什么这样抽**：
圈舍列表、档案列表、物资列表…… 十几个页面的逻辑几乎一样，如果每个页面都重写一遍分页、筛选重置、加载状态处理，会有十几个版本的 bug。抽成公共函数后，**修一次全站生效**。

**技术关键词**：组合式 API（`useXxx` 命名约定）、响应式状态（`ref` / `computed`）。

**没它会怎样**：分页/筛选逻辑在十几个文件里重复，改动要改十几处，漏一处就出 bug。

### 2.3 为什么快速切页数据不会乱跳

**现象**：在圈舍列表页快速切换畜种（牛→羊→猪），有时会看到"牛的数据"出现在"猪"的页面上。快速点筛选条件也一样。

**原因**：网络请求有快慢。如果"猪"的请求先发出但后返回，"牛"的请求后返回却先到，就会用旧数据覆盖新数据 —— 界面最终显示的是"牛"的数据，但用户已经切到猪了。

**技术**：请求竞态防护（`livestock-web/src/api/request.ts`）

**解决思路**：**给每个请求打序号，只认最后一次发出的**。

```typescript
const pendingGetSeq = new Map<string, PendingEntry>()   // key → 该请求的最新序号
let globalSeq = 0

// 请求发出前：登记序号
http.interceptors.request.use((config) => {
  const key = dedupKey(config)          // 由 "方法+URL+参数" 算出唯一 key
  const seq = ++globalSeq
  pendingGetSeq.set(key, { seq, ts: Date.now() })
  config._dedup = { key, seq }
  return config
})

// 响应回来时：序号不是最新的，直接丢弃
http.interceptors.response.use((response) => {
  const { key, seq } = response.config._dedup
  const current = pendingGetSeq.get(key)
  if (current && current.seq !== seq) {
    return Promise.reject(Object.assign(new Error('STALE_RESPONSE'), { __stale: true }))
  }
  // 序号是最新的 → 才返回给页面
  return response.data
})
```

**关键设计点**：

| 设计 | 为什么 |
|---|---|
| 只对 **GET** 做防护 | POST/PUT/DELETE 是用户主动提交的操作，丢弃会导致"点了没反应" |
| 用 `Map` + 时间戳清理 | 防止 Map 无限增长（60 秒无更新的记录会被删） |
| 参数排序后再拼 key | 保证 `?a=1&b=2` 和 `?b=2&a=1` 被认作同一个请求 |
| 丢弃时**静默** | 不弹错误提示 —— 旧响应本来就没意义了，弹错反而困扰用户 |

**没它会怎样**：用户会看到"数据串了"，在多畜种场景下特别容易误以为数据错误。

### 2.4 Excel 导入导出：惰性加载的智慧

**现象**：系统有"导出 Excel"和"从 Excel 导入"功能，但打开首页时并不会感觉慢。为什么？

**技术**：动态 import + 打包器分块（`livestock-web/src/utils/excel.ts`）

**问题根源**：处理 Excel 的库（`xlsx`）打包后有 **414 KB**。而数据大屏是登录后的默认首页，它只是"可能会用到导出"，如果静态引入，打开首页就白白下载这 414 KB。

**解法：把库藏进一个函数里**

```typescript
let xlsxModule: Promise<typeof import('xlsx')> | null = null

function loadXLSX(): Promise<typeof import('xlsx')> {
  if (!xlsxModule) xlsxModule = import('xlsx')   // 动态 import
  return xlsxModule
}

export async function exportToExcelAsync(filename, sheets) {
  const loading = ElLoading.service({ text: '正在生成 Excel...' })   // 先显示 loading
  try {
    const XLSX = await loadXLSX()                                    // 这时才下载 414 KB
    // ... 构建并导出
  } finally {
    loading.close()
  }
}
```

**这里有两个细节值得学**：

1. **`import()` 返回 Promise** —— 动态导入天然是异步的，所以所有用到它的函数都得是 `async`。这也是为什么 `downloadImportTemplate()` 从同步变成了异步（调用处需要补 `await`）。

2. **模块级缓存 Promise** —— 用变量记住已加载的库。第二次导出时直接复用，不会重复下载。用 Promise 而不是库本身，是为了**并发调用时不会重复触发加载**（如果两个导出几乎同时发生，只初始化变量是不够的，会发起两次下载）。

**验证方式**：构建产物里能看到 `excel-xxx.js` 只有 1.8 KB（工具函数本体），而真正的 414 KB 库被拆成了独立的 chunk，只有真正点击导出时才会被下载。

**技术关键词**：动态 import、代码分割（code splitting）、异步 chunk。

**没它会怎样**：每个页面首屏都多背 414 KB，手机端和弱网环境下打开会明显变慢。

### 2.5 数据大屏与 ECharts 按需加载

**问题**：ECharts 完整库打包后超过 1 MB，而本系统实际只用到了柱状图、饼图、折线图和几个组件。

**解法一：只注册需要的模块**（`livestock-web/src/views/dashboard/DashboardView.vue`）

```typescript
import { use } from 'echarts/core'
import { CanvasRenderer } from 'echarts/renderers'
import { BarChart, PieChart } from 'echarts/charts'
import { GridComponent, TooltipComponent, LegendComponent } from 'echarts/components'

use([CanvasRenderer, BarChart, PieChart, GridComponent, TooltipComponent, LegendComponent])
```

对比完整引入 `import * as echarts from 'echarts'` —— 后者会把全部图表类型都打进来。

**解法二：换轻量封装**（`livestock-web/src/components/TechChart.vue`）

项目没有直接用 `vue-echarts`，而是包了一层 `TechChart.vue`，统一处理主题注册和图表样式。好处是"用哪个图表都一样"，换主题只改一个文件。

**解法三：图表路由懒加载**

统计页面（5 个图表页）用动态 import，用户不点就不加载：

```typescript
{ path: ':species/statistics/breeding',
  component: () => import('@/views/statistics/BreedingStatsView.vue') }
```

**⚠️ 顺带一个今天遇到的坑**：
同一款软件里"图标库全量导入"是个常见陷阱。本项目原来的写法是：

```typescript
import * as Icons from '@element-plus/icons-vue'
for (const name of ICON_NAMES) { app.component(name, Icons[name]) }   // 动态属性访问
```

`import *` 配合**动态属性访问**（`Icons[name]`）会让打包器无法做 tree-shaking（摇掉没用的代码），结果整个图标库（300+ 个图标）全部进包。改成**具名导入**（`import { AlarmClock, Box, ... } from '...'`，共 31 个）之后，未用到的图标就能被剔除。

**这是判断"按需引入有没有真的生效"的关键**：不只看写了什么 import，还要看**写法上有没有阻断 tree-shaking**（动态属性访问、`import *` 都会阻断）。

## 第 3 章：业务自动化（系统的"聪明"在哪）

前面两章讲的是通用技术，这一章讲**这个项目特有的业务逻辑** —— 系统替人做了哪些判断。这些地方最能体现"业务和技术结合"。

### 3.1 耳标自动生成

**业务规则**：每头畜禽要有唯一编号（耳标）。规则是 **5 位**：

```
[畜种位 1 位] + [圈舍编号数字 2 位] + [入栏序号 2 位]
```

例：`A02` 号牛舍入栏第 7 头牛 → `1` + `02` + `07` = **10207**

**代码在哪**：`livestock_server/app/modules/pen/service.py` + `modules/animal/service.py`

```python
# pen/service.py —— 前缀（3 位）
SPECIES_TAG_DIGIT = {"牛": "1", "羊": "2", "猪": "3"}   # 畜种位

def parse_ear_tag_prefix(pen, species_override=None) -> str:
    species = species_override or pen.species
    if not species:
        raise BizException("圈舍尚未分配畜种，无法生成耳标", code=40021)
    digit = SPECIES_TAG_DIGIT.get(species)        # 取畜种位
    number = pen_tag_number(pen.pen_code)         # 从 "A02" 里抠出 "02"
    if not number:
        raise BizException("圈舍编号里没有数字，无法生成耳标", code=40021)
    return digit + number                        # "102"
```

**为什么要加"畜种位"**（代码注释里写明了原因）：
圈舍编号只在**畜种内**唯一 —— 牛场和羊场都可以有一个 `A02`。如果只用品舍数字，两个场的 A02 会生成同样的耳标，撞号。加上畜种位后 `102` 和 `202` 就分开了。

**序号分配的两条重要规则**：
1. **复用空号**：某个号对应的档案被删除后，这个号可以再发给新畜（`animal/service.py` 的 `generate_ear_tag`）
2. **兼容旧规则**：代码里有一段兼容逻辑 —— 即使圈里还留着旧版 4 位耳标，新序号也不会跟它们撞

**技术要点**：把"编号规则"做成**配置 + 纯函数**（`SPECIES_TAG_DIGIT` 是字典，函数无副作用），改规则只需改一处。

### 3.2 生长阶段自动判定

**业务规则**：畜禽按日龄自动归入不同发育阶段，牛有 4 个阶段，羊和猪的边界不一样。

**代码在哪**：`livestock_server/app/modules/animal/service.py`

```python
GROWTH_STAGE_CONFIG = {
    "牛": [("犊牛期", 1, 60), ("保育期", 61, 180), ("生长期", 181, 365), ("育肥期", 366, 540)],
    "羊": [("羔羊期", 1, 45), ("保育期", 46, 90), ("生长期", 91, 180), ("育肥期", 181, 270)],
    "猪": [("仔猪期", 1, 28), ("保育期", 29, 70), ("生长期", 71, 120), ("育肥期", 121, 180)],
}

def determine_growth_stage(species: str, age_days: int) -> str:
    stages = GROWTH_STAGE_CONFIG.get(species)
    if not stages:
        raise BizException(f"不支持的畜种：{species}", code=40020)
    if age_days < stages[0][1]:
        return stages[0][0]          # 边界处理：日龄不足第一档时按第一档算
    for name, start, end in stages:
        if start <= age_days <= end:
            return name
```

**设计亮点：配置驱动**。
如果把规则写成 `if species == "牛" and age < 60: ...` 的一长串 if，新增畜种要改很多地方。改成"配置表 + 通用算法"后，加一个畜种只需在字典里加一行。

**触发时机**：不靠用户手动改，而是每天凌晨由定时任务批量刷新（见 [4.7](#47-定时任务apscheduler)）。

**优先级设计**：代码注释说明"妊娠期由配种记录单独标记，优先级高于这些基础阶段" —— 所以一头怀孕的母牛，在生长阶段表里仍然是"生长期"，但业务上会额外标记"妊娠"。

### 3.3 预产期与繁育预警

**业务规则**：配种后自动算预产期；到时间了自动提醒。

**代码在哪**：`livestock_server/app/modules/breeding/service.py` + `app/scheduler.py`

**第一步：预产期自动计算**（写配种记录时立即算）

```python
GESTATION_DAYS = {"牛": 280, "羊": 150, "猪": 114}

gestation_days = GESTATION_DAYS.get(body.species, 0)
expected_birth_date = body.mating_date + timedelta(days=gestation_days)
```

**第二步：预警规则用常量表达**（`app/scheduler.py`）

```python
PREGNANCY_CHECK_DAYS = 60   # 配种后满 60 天 → 孕检提醒
BIRTH_REMIND_DAYS = 15      # 预产期前 15 天 → 临产提醒
HEAT_REMIND_DAYS = 60       # 产犊后满 60 天仍无配种 → 未发情提醒
```

**第三步：防重复触发**（`scheduler.py` 的 `_alert_exists`）

```python
def _alert_exists(db, farm_id, animal_tag, alert_type, alert_date) -> bool:
    return db.query(BreedingAlert).filter(
        BreedingAlert.farm_id == farm_id,
        BreedingAlert.animal_tag == animal_tag,
        BreedingAlert.alert_type == alert_type,
        BreedingAlert.alert_date == alert_date,
    ).first() is not None
```

同一天、同一头、同一类型的预警只生成一次 —— 否则每晚定时任务都会重复插入，数据库会被塞满垃圾数据。

**技术要点**：定时任务 + 幂等性设计。**任何"每天自动跑"的任务都要考虑幂等**，否则重复运行就会产生重复数据。

### 3.4 库存与加权平均成本

**业务规则**：进货审核通过后库存自动增加，同时更新均价；均价用**移动加权平均**，不是"按最近一次价格"。

**代码在哪**：`livestock_server/app/modules/inventory/service.py`

**均价计算**（`_sync_purchase_to_stock`）：

```python
old_price = float(stock.unit_price or 0)
stock.unit_price = round(
    (old_qty * old_price + in_qty * float(p.cost_price)) / stock.quantity, 2)
```

翻译成人话：原来有 100 件、均价 10 元；新进 100 件、单价 12 元。
新均价 = (100×10 + 100×12) ÷ 200 = **11 元**，而不是 12 元（也不是 10 元）。

**为什么用加权平均**：进货价每次都变，如果用"最新价"，库存成本会剧烈波动；用加权平均能让成本平滑，反映真实。

**第二处细节：领用时存单价快照**（`service.py` 第 463 行）

```python
unit_price=float(stock.unit_price or 0),  # 单价快照，防止后续进货改价影响历史成本
```

领用记录里**复制**一份当时的价格，而不是引用库存的当前均价。
否则下次进货改了均价，**历史领用记录的成本会被追溯篡改** —— 账就乱了。

**技术要点**：区分"当前状态"和"历史快照"。凡是不可回溯修改的数据（成本、成交价），都必须存快照。

**第三处细节：双次校验库存充足**

员工提交领用时校验一次（体验），场主审核时再校验一次（防并发）。
如果只在提交时校验，两个员工同时提交各 100 件、库存只有 150 件，就会超领。

### 3.5 审核流：一个可复用的状态机

**业务规则**：员工提交的记录不是直接生效，而是"待审核"，场主确认后才计入库存和统计。

**涉及的六类记录**：饲喂、进货、领用、防疫、诊疗、配种。

**技术实现**：统一的 `audit_status` 字段 + 审核中心聚合

```python
# 各业务表都带一个同名的状态字段，默认值统一为"待审核"
MatingRecord.audit_status = Column(String(10), default="待审核",
                                   comment="审核状态：待审核/通过/驳回")

# 状态机只有两个出口，由场主在审核中心决定
待审核 ──审核通过──▶ 通过    # 记录正式生效，参与库存增减与统计
待审核 ──审核驳回──▶ 驳回    # 记录保留，但不计入统计
```

审核中心用一张配置表把六类业务聚合到同一个入口（`modules/review/service.py`）：

```python
BUSINESS_NAMES = {
    "feeding": "饲喂记录", "purchase": "进货记录", "consume": "领用记录",
    "vaccine": "防疫记录", "medical": "诊疗记录", "mating": "配种记录",
}
```

各模块的审核接口还会校验传入值，防止写入非法状态：

```python
if body.audit_status not in ("通过", "驳回"):
    raise BizException("审核状态只能填：通过 / 驳回", code=40045)
```

**统一状态字段的收益**：
六类业务共用同一个字段名（`audit_status`）和同一套取值，审核中心才能用一份代码聚合全部。如果每类记录各写一套审核逻辑，六份代码里只要有一份漏掉状态判断，统计口径就会出错。

**关键约束：已审核的记录不允许删除**（`inventory/service.py`）

```python
def delete_purchase(db, farm_id, purchase_id):
    p = get_purchase(db, farm_id, purchase_id)
    if p.audit_status == "通过":
        raise BizException("已审核通过的记录不能删除", code=40062)
    p.deleted = True
    ...
```

原因很实在：**库存已经因为这条记录变了**（加了数量）。如果允许删掉记录，库存就再也对不上了。这是"日志不可变"思想的应用 —— 已经产生业务影响的记录只能作废（改状态），不能删除。

**审核结果的通知闭环**：审核完成后调用 `system_service.send_message()` 给提交人发站内消息，提交人下次登录能看到"你提交的记录已通过/被驳回"。这条链路串起了审核模块和站内消息模块。

**技术要点**：跨模块协作通过 service 层调用（`modules/review/service.py` 导入 `modules/system/service.py`），而不是模块之间直接操作对方的表。

## 第 4 章：后端是怎么搭的

### 4.1 FastAPI：接口文档自动生成

**一句话**：写完接口代码，文档自动出来，还能直接在线试调。

**技术**：FastAPI（Python 的现代 Web 框架）

**启动后打开 `http://127.0.0.1:8000/docs` 会看到什么**：
- 所有接口的列表（按模块分组）
- 每个接口的参数说明、必填项
- 一个可以直接填参数点"执行"的测试按钮

**关键设计：接口声明自带文档信息**

```python
@router.post("/pen/add", summary="新增圈舍")
def add_pen(body: PenIn,
            db: Session = Depends(get_db),
            current_user: User = Depends(get_current_user)):
    ...
```

只要写了类型注解（`body: PenIn`、`db: Session`），FastAPI 就知道：
- 这个接口要收一个 JSON 请求体，结构是 `PenIn`（自动生成校验规则和文档）
- `Depends(get_db)` 这个参数由框架注入，不是前端传的

**FastAPI 自动做的三件事**：
1. **参数校验**：前端少传字段、类型不对，直接返回明确的错误，不会执行到业务代码
2. **接口文档**：自动生成 `/docs` 页面
3. **异步能力**：FastAPI 基于 ASGI，天然支持高并发（虽然本项目用的是同步 SQLAlchemy，通过线程池执行）

**对比传统 Flask**：Flask 需要额外写 `flask-restful` 或手动维护 docstring 才有文档，参数校验要手写。FastAPI 把这些做成了默认行为。

**没它会怎样**：要么接口文档靠人手写（容易和代码不同步），要么参数校验漏了导致脏数据进库。

---

### 4.2 SQLAlchemy ORM：不用手写 SQL 也能操作数据库

**一句话**：把数据库的表写成 Python 类，用类的方法来查数据，不用手写 `SELECT ...`。

**技术**：SQLAlchemy 2.x + 声明式模型

**表在代码里长这样**（`modules/pen/model.py`）：

```python
class Pen(BasePO):
    """圈舍表"""
    __tablename__ = "pen_info"
    pen_code  = Column(String(50), nullable=False, comment="圈舍编号")
    pen_type  = Column(String(10), nullable=False, comment="类型：A育雏/B育成/C繁育/D种畜")
    capacity  = Column(Integer, nullable=False, default=0, comment="容量")
    species   = Column(String(10), nullable=True, comment="畜种")
```

`Column(..., comment="...")` 里的注释会直接进入数据库表结构的备注里 —— 这是一个成本很低的好习惯，数据库文档和代码永远同步。

**查询怎么写**（不用一行 SQL）：

```python
pens = db.query(Pen).filter(
    Pen.farm_id == current_user.farm_id,      # 多租户隔离
    Pen.deleted == False,                    # 软删除过滤
    Pen.pen_type == "A",                     # 业务条件
).order_by(Pen.id.desc()).offset(20).limit(10).all()
```

**对应的 SQL** 由 SQLAlchemy 生成。好处：
- 数据库换了（MySQL→SQLite）不用改代码
- 拼接条件可以复用变量，不会出现 SQL 注入
- 代码可读性比字符串拼接 SQL 好得多

**软删除（重要设计）**：
上面所有的查询都带 `deleted == False`。删除数据时不是真的 `DELETE`，而是把 `deleted` 标记设为 `True`：

```python
def delete_pen(db, farm_id, pen_id):
    pen = get_pen(db, farm_id, pen_id)
    pen.deleted = True
    db.commit()
```

**为什么要这样**：外键关联、审计追溯需要历史数据保留。真的删了，`animal` 表里那些指向这个圈舍的记录就变成了"指向不存在的数据"的孤儿。

**对应到 SQLAlchemy 写法**：`Where条件` 里的字段名写成 `SysMenu.deleted`（`SysMenu.deleted == False`），底层会映射到 `sys_menu.deleted = 0`。

**没它会怎样**：手写 SQL 字符串拼接，轻则代码难读，重则 SQL 注入漏洞（把用户输入直接拼进 SQL）。

### 4.3 四层分工：model / schema / service / api

**一句话**：每个业务模块的文件不是随便堆的，而是固定分四层，各管一件事。

**目录结构**（以圈舍模块为例）：

```
modules/pen/
├── model.py     ← 数据长什么样（表结构）
├── schema.py    ← 数据怎么传进传出（接口的"入参/出参"）
├── service.py   ← 业务规则怎么算（真正的逻辑）
├── api.py       ← 接口地址怎么定义（路由）
└── __init__.py
```

**每层的职责和为什么分开**：

| 层 | 职责 | 不该做什么 | 为什么分开 |
|---|---|---|---|
| `model` | 表结构 | 不写业务逻辑 | 数据库结构变更频繁，改表不该动逻辑 |
| `schema` | 请求/响应的数据格式 | 不碰数据库 | 前端要的字段和数据库字段常常不一样（比如 `password_hash` 不能给前端） |
| `service` | 业务规则 | 不关心 HTTP | 业务规则可以被定时任务、其它模块复用，不依赖 HTTP |
| `api` | 路由定义 | 不写业务 | 接口地址变了不影响业务逻辑 |

**实际例子：新增圈舍**

```python
# api.py —— 只管路由和参数
@router.post("/add", summary="新增圈舍")
def add_pen(body: PenIn, db: Session = Depends(get_db),
            current_user: User = Depends(get_current_user)):
    pen = pen_service.add_pen(db, body, current_user.farm_id)
    return Result.ok(data=PenOut.model_validate(pen), msg="添加成功")

# service.py —— 只管业务
def add_pen(db, body, farm_id) -> Pen:
    if pen_code_exists(db, farm_id, body.pen_code):
        raise BizException(f"圈舍编号 {body.pen_code} 已存在", code=40041)
    pen = Pen(**body.model_dump(), farm_id=farm_id)
    db.add(pen)
    db.commit()
    return pen
```

**好处很具体**：
- 定时任务里也能调 `pen_service.add_pen()`，完全不需要构造 HTTP 请求
- `BizException("圈舍编号已存在", code=40041)` 这个业务错误，service 不需要知道 HTTP 返回什么格式，异常处理器会统一转成响应

**没它会怎样**：所有逻辑写在一个文件里，改一个接口要通读几百行；定时任务想复用逻辑只能复制粘贴。

### 4.4 依赖注入：把"检查"交给框架

**一句话**：把"每个接口都要做的准备工作"（查数据库、验证登录、校验权限）声明在接口上，框架自动帮你执行。

**技术**：FastAPI 的 `Depends` 机制

**三种依赖，项目里都在用**：

```python
# ① 拿数据库会话 —— 所有需要查库的接口
db: Session = Depends(get_db)

# ② 拿当前登录用户 —— 所有需要身份的接口
current_user: User = Depends(get_current_user)

# ③ 校验模块权限 —— 需要 RBAC 的接口
router = APIRouter(dependencies=[Depends(require_perms("feeding"))])
```

**`get_db` 为什么必须用依赖**（`app/database.py`）：

```python
def get_db():
    db = SessionLocal()
    try:
        yield db              # 把数据库会话交给接口用
    finally:
        db.close()            # 无论接口成功还是报错，都确保关闭连接
```

**`yield` 是关键** —— FastAPI 支持"生成器形式的依赖"：先执行 `yield` 前面的代码，把结果交给接口；接口执行完（包括抛异常）再执行 `finally` 清理。

**这解决了一个真实问题**：数据库连接池会耗尽。如果连接不关闭，跑一天后接口就全部卡死。用依赖 + `finally` 就能保证一定释放。

**依赖还能嵌套**：`require_perms` 内部又依赖 `get_current_user` 和 `get_db`，FastAPI 会自动解析依赖树并保证每个依赖只执行一次。

### 4.5 统一响应与全局异常

**问题**：如果每个接口自己 `return` 各种格式，前端就得写一堆判断：

```python
return {"code": 200, "data": [...]}
return {"status": "ok", "result": [...]}
return {"success": True, "items": [...]}
```

**解法一：统一响应包装**（`app/core/response.py`）

```python
# 业务代码里这样写
return Result.ok(data=pen_list, msg="添加成功")
return Result.ok(data=result)          # 分页数据直接塞 data
```

统一成 `{"code": 200, "msg": "...", "data": ...}` 三段式。前端 `request.ts` 里一处判断 `data.code !== 200` 就能处理所有情况。

**解法二：异常也统一处理**（`app/core/exceptions.py` + `main.py`）

```python
app.add_exception_handler(BizException, biz_exception_handler)
app.add_exception_handler(RequestValidationError, validation_exception_handler)
app.add_exception_handler(Exception, global_exception_handler)
```

**业务代码只要抛异常，不用自己处理返回**：

```python
if not pen:
    raise BizException("圈舍不存在", code=40046)
```

前端收到的一定是标准格式：`{"code": 40046, "msg": "圈舍不存在"}`，然后 `request.ts` 统一弹出这个 msg。

**三层异常的分工**：

| 异常 | 从哪来 | 怎么返回给用户 |
|---|---|---|
| `BizException` | 业务规则不满足（如"编号已存在"） | 返回 code + 明确的中文 msg |
| `RequestValidationError` | FastAPI 参数校验失败（如少传字段） | 返回 400 类错误 + 字段提示 |
| `Exception` | 未预期的错误（空指针、数据库挂了） | 记日志，返回通用错误信息（不泄露内部细节） |

**⚠️ 安全提示**：最后一层很重要 —— 未预期的异常**不能把 Python 堆栈返回给前端**，那会泄露文件路径和代码结构。`global_exception_handler` 的职责就是兜住这类情况。

### 4.6 操作日志中间件

**业务需求**：谁在什么时候做了什么操作，需要留痕（用于审计）。

**技术**：FastAPI 中间件（Middleware）

**代码在哪**：`livestock_server/app/main.py` 的 `oper_log_middleware`

**中间件的工作方式**：它包在所有接口外面，像一个门卫：

```
请求进来 → 中间件先过 → 路由处理 → 中间件再过 → 响应出去
```

**本项目只记录写操作**：

```python
@app.middleware("http")
async def oper_log_middleware(request, call_next):
    method = request.url.path
    if method not in ("POST", "PUT", "DELETE") or not path.startswith("/api/"):
        return await call_next(request)      # GET 直接放行，不记录
    ...
```

**为什么不记录 GET**：查询操作量大（用户翻页、筛选都会产生 GET），全记会淹没真正的操作记录。写操作才有审计价值。

**实现里有个必须处理的坑**：

```python
# 缓存响应体后再回放：BaseHTTPMiddleware 的流式响应没有 .body 属性
body_bytes = b""
async for chunk in response.body_iterator:
    body_bytes += chunk.encode("utf-8") if isinstance(chunk, str) else chunk
...
return Response(content=body_bytes, status_code=response.status_code, headers=dict(response.headers))
```

中间件要记录"这次操作成功还是失败"，就必须**先读到响应内容**。但 Starlette 的中间件拿到的是流式响应，没有 `.body` 属性。代码里注释提到一个历史 bug：**老实现恒取到 `None`，导致所有操作日志一律记成功** —— 失败的记录也被记成成功。

**解法**：手动把流读完缓存起来，再重新构造一个 `Response` 返回。所以能读到 `{"code": 500}` 这样的错误响应，从而正确判断状态。

**数据库操作不阻塞主线程**：

```python
await run_in_threadpool(_write_oper_log, request, method, user_id, status, error_msg)
```

同步的数据库写入放到线程池执行，避免阻塞事件循环导致其他请求变慢。

**技术要点**：中间件适合"每个请求都要做的事"（日志、鉴权、跨域）；但因为要读响应体，它会让响应从流式变成完整缓冲，**有额外开销**。所以本项目才加了 `if method not in (...) : 直接放行` 的短路。

### 4.7 定时任务（APScheduler）

**业务需求**：每天凌晨自动维护数据，不需要人工点。

**技术**：APScheduler 的 BackgroundScheduler（`livestock_server/app/scheduler.py`）

**注册了 4 个任务**：

```python
scheduler.add_job(refresh_growth_stages,     "cron", hour=0, minute=5,  id="refresh_growth")
scheduler.add_job(scan_breeding_alerts,      "cron", hour=0, minute=10, id="breeding_alert")
scheduler.add_job(refresh_material_stock_status, "cron", hour=0, minute=20, id="stock_status")
scheduler.add_job(clean_animal_history,      "cron", hour=0, minute=30, id="clean_history")
```

| 时间 | 任务 | 干什么 |
|---|---|---|
| 00:05 | 刷新生长阶段 | 按出生日期重算所有在栏畜禽的阶段 |
| 00:10 | 扫描繁育预警 | 生成孕检/临产/未发情提醒 |
| 00:20 | 刷新库存状态 | 标记过期/缺货物资 |
| 00:30 | 清理历史档案 | 删掉超过 180 天的历史记录 |

**错开时间点**（5/10/20/30 分）不是随便定的 —— 凌晨负载低，但仍要避免多个任务同时抢数据库连接。

**生命周期管理**（`app/main.py`）：

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    init_db()          # 启动时：建表 + 初始化数据
    start_scheduler()  # 启动时：开启定时任务
    yield              # ← 应用运行期间
    shutdown_scheduler()  # 关闭时：清理
```

用 `lifespan`（生命周期钩子）来管理启动和关闭，能保证**进程退出时定时任务被正确关闭**，不留下悬挂线程。

**每个任务函数都有相同的防护结构**：

```python
def refresh_growth_stages():
    db = SessionLocal()
    try:
        ...业务逻辑...
        db.commit()
    except Exception as e:
        db.rollback()        # 出错回滚，避免脏数据
        _log(f"生长阶段刷新失败：{e}")
    finally:
        db.close()           # 一定要关连接
```

**技术要点**：定时任务最容易出问题的三点 —— 连接没关、异常没兜住、重复执行产生脏数据。这段代码正好各做了一次处理。

## 第 5 章：工程化取舍

前面五章讲"怎么实现"，这一章讲"为什么这么实现" —— 都是为了性能或可维护性做的技术选择。

### 5.1 元素按需加载：让用户少下载东西

**背景**：一个管理后台的技术栈很重 —— Vue + Element Plus + ECharts + xlsx，全部打包有 2 MB 以上。开发时 Vite 按需加载做得不好，会明显拖慢首屏。

**四项措施**：

| 措施 | 代码 | 效果 |
|---|---|---|
| 组件按需引入 | `vite.config.ts` 的 `AutoImport` + `Components` 插件 | 只打包用到的 Element Plus 组件和样式 |
| 图标具名导入 | `utils/icons.ts`（原为 `import *`） | 图标库从全量变 31 个 |
| 依赖预构建 | `optimizeDeps.include` 显式列出深层依赖 | 开发时不"现场发现新依赖" |
| 大库惰性加载 | `utils/excel.ts`（414KB） | 只在点导出时才下载 |

**依赖预构建这一条值得展开**（踩过坑）：

Element Plus 按需引入会产生 `element-plus/es/components/<name>/style/css` 这类**深层导入**，Vite 启动时扫描不到它们。于是页面首次用到某个组件时才现场发现新依赖 → 重新预构建 → **整页强制刷新**（`optimized dependencies changed. reloading`），点菜单就"闪一下"。

解决：在 `vite.config.ts` 的 `optimizeDeps.include` 里显式列出。但这里有个陷阱：

```typescript
// ❌ 无效：optimizeDeps.include 里的通配符是在**文件系统**上展开的
include: ['element-plus/es/components/*/style/css']
//   真实文件名是 css.mjs，匹配不到任何文件，且**不会报错**，静默失效

// ✅ 有效：读取磁盘上真实存在的样式文件
const EP_DIR = resolve(__dirname, 'node_modules/element-plus/es/components')
const epStyleDeps = existsSync(EP_DIR)
  ? readdirSync(EP_DIR)
      .filter((name) => existsSync(resolve(EP_DIR, name, 'style/css.mjs')))
      .map((name) => `element-plus/es/components/${name}/style/css`)
  : []
```

**这个坑的通用教训**：**"配置了但没报错"比"配置错了直接报错"更危险**。做优化时一定要验证结果（看构建产物），不能只看代码写没写。

**没它会怎样**：开发时点菜单频繁闪白页、重新编译；生产环境首屏多下载几百 KB。

---

### 5.2 跨域与开发代理

**问题**：前端跑在 5173，后端跑在 8000。浏览器默认禁止网页请求**不同端口**的服务（跨域）。

**传统解法（也是本项目后端的做法）**：后端设置 CORS 响应头，放行前端域名。

```python
# app/main.py
app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:5173", "http://127.0.0.1:5173", *_cors_extra],
    allow_origin_regex=r"http://(localhost|127\.0\.0\.1):\d+",   # 端口不固定，用正则放行
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

**为什么用正则**：`allow_origin_regex` 是为了应对"Vite 端口被占用自动换到 5174"的情况 —— 硬编码 5173 会导致换端口后立刻报跨域错误。

**更好的解法（Vite 开发代理）**：

让**前端自己转发**：配置 Vite 代理后，浏览器看到的所有请求都是 5173 同源地址，Vite 在服务端把 `/api` 转给 8000。浏览器完全不涉及跨域。

```typescript
// vite.config.ts
server: {
  proxy: {
    '/api': { target: 'http://127.0.0.1:8000', changeOrigin: true },
  },
}
```
```ini
# .env.development
VITE_API_BASE=/api/v1        # 相对路径，同源
```

**两种方案的对比**：

| | 后端 CORS | Vite 代理 |
|---|---|---|
| 生效范围 | 所有环境 | 仅开发环境 |
| 浏览器跨域预检 | 需要（多一次 OPTIONS 往返） | 不需要（同源） |
| 生产是否可用 | 可用 | 不可用（需 Nginx 反代） |
| 代码侵入性 | 后端要写死放行列表 | 只需改一行配置 |

**本项目两者都做了**：开发用 Vite 代理（快、无跨域），生产由 Nginx 反代（同样同源）。后端的 CORS 作为兜底保留。

**⚠️ 一致性问题**：`.env.development` 和 `.env.production` 必须用**同一套相对路径**，否则开发好好的、生产出问题。早期开发环境配的是绝对地址（`http://127.0.0.1:8000/api/v1`），改成相对路径后 Vite 代理才真正生效 —— 同时也消除了每次请求多一次预检的开销。

### 5.3 数据库自迁移

**问题**：项目开发过程中表结构会变（加字段、改类型）。传统做法是用专门的迁移工具（Django migrations、Flyway、Alembic）管理版本。

**本项目的做法**：把迁移写进启动流程。

```python
# app/main.py
def init_db():
    Base.metadata.create_all(bind=engine)      # ① 自动建表（已存在的不会覆盖）
    db = SessionLocal()
    try:
        _ensure_sys_role_perms(db)              # ② 老库缺列 → 补
        _ensure_stock_unit_price(db)            # ③ 老库缺列 → 补 + 回填存量数据
        _ensure_sys_notice_farm_id(db)          # ④ 老库缺列 → 补 + 关联历史数据
        _ensure_pen_species(db)
        _ensure_mating_audit_status(db)
        ...
    finally:
        db.close()
```

**每个 `_ensure_*` 的模式都一样**（以补列为例）：

```python
def _ensure_sys_notice_farm_id(db):
    from sqlalchemy import text
    try:
        rows = db.execute(text(
            "SELECT COLUMN_NAME FROM INFORMATION_SCHEMA.COLUMNS "
            "WHERE TABLE_NAME='sys_notice' AND COLUMN_NAME='farm_id'"
        )).fetchall()
        if not rows:                                    # 列不存在才处理
            db.execute(text("ALTER TABLE sys_notice ADD COLUMN farm_id INT"))
            db.execute(text("UPDATE sys_notice SET farm_id = (...) WHERE farm_id IS NULL"))
            db.commit()
    except Exception as e:
        print(f"跳过：{e}")
        db.rollback()                                    # 失败不影响启动
```

**三个设计要点**：

1. **先查询再执行** —— 不重复 ALTER，不会因为"已经执行过"而报错
2. **`try/except` 兜住所有异常** —— 迁移失败不能阻止应用启动
3. **兼容不同数据库** —— `INFORMATION_SCHEMA` 是 MySQL 语法，SQLite 不支持，所以失败走 except 分支

**⚠️ 这套做法的取舍**（要知道它的局限）：

| | 自迁移 | 正式迁移工具（Alembic） |
|---|---|---|
| 优点 | 简单、零依赖、启动即同步 | 有版本号、可回滚、可追踪每次变更 |
| 缺点 | **没有回滚能力**，改动历史不可追溯 | 需要学习成本、需维护迁移脚本目录 |

**判断标准**：**表结构变更频繁的团队用 Alembic，这个项目用自迁移**。因为它项目小、变更少，够用且省事。

### 5.4 字典：留给未来的扩展口

**问题**：如果"品种""疫苗类型""物资类型"这些值硬编码在代码里，每加一个新品种都要改代码、重新发布。

**本项目的方案**：

```
sys_dict_type（字典类型）        sys_dict_data（字典数据）
├─ sys_breed   品种             ├─ dict_type = "sys_breed"
│                               ├─ dict_label = "西门塔尔"     ← 显示用
├─ sys_mating_type 配种方式      ├─ dict_value = "西门塔尔"     ← 存储用
├─ sys_material_type 物资类型    └─ dict_extra = '{"species":"cattle"}'  ← 扩展信息
├─ sys_pen_type 圈舍类型
└─ ... 共 13 类 57 条
```

**关键字段 `dict_extra`**（JSON 文本）是这个设计最巧的地方：

品种下拉框要显示"牛场只能选牛的品种"。品种本身只是名字（"西门塔尔"），怎么知道它属于牛？

```python
# 前端 composables/useSpecies.ts 里的过滤逻辑
const extra = JSON.parse(d.dict_extra || '{}')
return !extra.species || extra.species === species.value   // 当前畜种匹配才显示
```

**用 JSON 字符串塞附加属性**，好处是**加新维度不用改表结构**。如果今天要加"产地"，只需在 `dict_extra` 里多存一个 key，代码里多读一个字段。

**数据是怎么进字典的**：
```python
# service.py 启动时执行（init_dict_data）
for dtype, label, value, sort, extra in DICT_DATA:
    db.add(DictData(dict_type=dtype, dict_label=label, dict_value=value,
                    dict_sort=sort, dict_extra=extra, status=1))
```

**⚠️ 当前状态**：字典数据在后台正常工作（品种下拉、防疫疫苗白名单等都依赖它），但**提供图形化维护的「字典管理」页面已下线**（2026-10-10）。

这带来一个副作用：**增加新品种目前只能改数据库或写脚本**。详见 [第 7 章](#第-7-章-已知技术债与可改进点)。

**技术要点**：**把"变化的业务数据"从"固定的代码"里抽出来**。这是应对需求变更最有效的手段 —— 加品种从"改代码+发版"变成"加一行数据"。

## 第 7 章：已知技术债与可改进点

这一章记录**当前实现中存在的问题**。写在这里是为了让接手的人知道边界在哪，而不是踩了坑才发现。

### 7.1 四个模块缺少后端权限校验（已于 2026-10-10 修复）

> 这节保留下来是为了记录这个坑是怎么产生的 —— 修完之后，同样的遗漏仍可能出现在新模块上。

**曾经的问题**：权限依赖 `require_perms("模块名")` 只挂在 6 个业务模块的 router 上：

```
有校验：pen、animal、feeding、health、inventory、breeding   （6 个）
无校验：review（审核）、finance（销售财务）、salary（薪资配置）、statistics（统计）  （4 个）
```

这 4 个模块只校验了"是否登录"（`Depends(get_current_user)`），**没有校验角色权限**。

具体后果：员工账号在前端看不到"销售订单"菜单，但**直接在浏览器控制台调用 `/api/v1/finance/sale/list`，接口会正常返回数据**（他已登录，而该接口没有 `require_perms`）。

**为什么容易被忽略**：
- 前端菜单做了隐藏，看起来"访问不到"
- 这类接口是后期需求变更时补的，忘了跟着加 `require_perms`
- 前端路由守卫有 `catch { /* 放行 */ }` 的兜底设计（意为"靠后端兜底"）—— 但这里恰恰是后端没兜住

**修复结果**（四个模块各加一行）：

| 模块 | 挂载的权限 key | 说明 |
| --- | --- | --- |
| `modules/review` | `review` | 审核是场主职责 |
| `modules/finance` | `finance` | 销售 / 成本 / 利润 / 薪资记录 |
| `modules/statistics` | `statistics` | 含财务统计，仅超管与场主 |
| `modules/salary` | **`farm`** | ⚠️ 见下方说明，不能直接写 `salary` |

```python
# 例：modules/finance/api.py
from app.core.perms import require_perms
router = APIRouter(dependencies=[Depends(require_perms("finance"))])
```

**⚠️ 修复时踩到的一个判断点：salary 不能直接写 `require_perms("salary")`**

后端 `modules/salary` 的接口是「**薪资配置**」的 CRUD（挂载在 `/api/v1/salary`，tags="薪资配置模块"），
对应前端的 `farm/salary`（**养殖场管理** → 薪资配置）。而 `RBAC_MODULES` 里**没有 `salary` 这一项**：

```python
RBAC_MODULES = ["dashboard","farm","pen","animal","feeding",
                "inventory","health","breeding","review","finance","system","statistics"]
```

如果硬写 `require_perms("salary")`，场主的权限集合来自 `RBAC_MODULES`（除 system），里面同样没有 `salary`
→ **连场主访问薪资配置都会被拒**，功能直接坏掉。

正确做法是挂 **`farm`**（薪资配置在"养殖场管理"菜单下），并与薪资**记录**区分开：

| 前端页面 | 后端模块 | 权限 key |
| --- | --- | --- |
| `farm/salary` 薪资**配置** | `modules/salary` | `farm` |
| `finance/salary` 薪资**记录** | `modules/finance` | `finance` |

**修复后的验证**（真实账号实测）：

| 接口 | 超管 | 员工（饲喂员） |
| --- | --- | --- |
| 薪资配置 / 成本支出 / 统计大屏 / 审核中心 | 200 | **40303 无权限访问该模块** |
| 圈舍列表 / 饲喂记录（对照，员工原有权限） | 200 | 200（未误伤） |

**这次没有收紧员工的可见范围**：员工角色（`ROLE_PERMS` 的 feeder/vet/breeder/keeper）本来就不含
review/finance/statistics，前端 `modulesOf()` 对员工还有第二层 `hasPerm()` 过滤，所以员工此前也看不到这些菜单
—— 后端补上校验属于"补齐缺口"，不是"新增限制"。

**遗留建议**（未做）：把可用模块名在 `core/perms.py` 里收成常量并配单测，
防止以后新增模块时再次遗漏。这次是 4 个模块同时漏掉，靠人工记忆并不保险。

### 7.2 品种维护没有图形化入口

**现象**：品种等字典数据存放在 `sys_dict_data`（13 类 57 条），业务下拉框都依赖它。但提供维护界面的「字典管理」页面已于 2026-10-10 下线（前端入口 + 后端接口均关闭）。

**影响**：增加新品种目前只能改数据库或写脚本。

**可能的处理方向**（三选一）：

| 方案 | 说明 | 适用 |
|---|---|---|
| 恢复字典管理页 | 只恢复"字典数据"的管理界面，不恢复字典类型管理 | 运维人员需要自主维护时 |
| 换成品种专用页 | 做一个"品种维护"页，表单更贴合业务（品种名 + 所属畜种），底层仍写字典表 | 演示效果好、业务更直观 |
| 保持现状 | 品种变更频率极低（几年一次），写脚本/改库足够 | 追求最少功能 |

**注意**：品种目前只是**档案标签**。系统的生长阶段、圈舍分配、饲喂、繁育口径全部按**畜种（牛/羊/猪）**计算，不按品种区分。所以品种维护的紧迫性不高。

### 7.3 菜单管理页面天然无效（已下线）

**背景**：早期版本从若依（RuoYi）这类后台框架移植过来，带了"菜单管理"页面。但本系统的侧边栏菜单是**前端静态配置**的（`Sidebar.vue` 的 `MODULES` 常量 + 静态菜单项），后端 `sys_menu` 表**不驱动**任何实际渲染。

**所以**：在菜单管理页面里增删改菜单，界面上不会有任何变化。已于 2026-10-10 下线。

**残留**：`sys_menu` 表仍在使用，但用途变成了两件事 —— 登录时 `/auth/permissions` 返回"可见菜单"给前端参考，以及 `init_rbac_data` 初始化 RBAC 数据。

**如果将来要做"可配置菜单"**（运营人员能在界面上改侧边栏），需要一次真正的改造：前端菜单改成从接口读取并动态渲染，当前这套静态配置就要推翻。
