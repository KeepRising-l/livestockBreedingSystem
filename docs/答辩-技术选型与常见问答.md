## 第 0 章 30 秒开场：一句话说清这个系统

老师第一个问题往往是"你这个系统是什么，做了什么"。开口 30 秒内要让评委抓住三件事：

> "我做的是一个面向中小型养殖场的**全流程信息管理系统**。它把养殖场从**入栏 → 饲喂 → 防疫诊疗 → 繁育 → 审核 → 库存 → 出栏销售**的整条链路数字化，用**一套统一的审核状态机**把员工提交、场主审批的业务闭环串起来，同时支持**一个部署实例服务多个养殖场**（多租户数据隔离）。
> 技术上是**前后端分离**的：后端 Python + FastAPI + SQLAlchemy + MySQL，前端 Vue 3 + TypeScript + Element Plus。"

**背下这三句**：① 业务闭环；② 统一审核状态机；③ 多租户 SaaS 形态。后面所有问题都能挂到这三根柱子上。

## 第 2 章 后端选型：逐个回答"为什么不用 X"

### 2.1 为什么用 FastAPI 而不是 Django？

这是最高频的一问，回答要**先定性再展开**：

**回答要点（按顺序说）**

1. **项目性质决定框架**：本系统前端是独立的 Vue SPA，后端**只提供 JSON API**，不需要 Django 的模板引擎、Forms、Admin、Session 那一整套"全栈全家桶"。用 Django 反而要引入 DRF（Django REST Framework）再包一层，等于在重量级框架上再装一层抽象。
2. **自带接口文档**：FastAPI 基于 OpenAPI 规范，启动后 `/docs` 直接可交互调试。[事实] `app/main.py` 里 `FastAPI(title=..., description=..., version=...)`，13 个模块全部挂在 `/api/v1` 下。**文档即接口契约**，前后端联调不需要手写接口文档再对一遍。
3. **参数校验与类型安全**：用 Pydantic 模型声明入参，类型不对、字段缺失在进业务代码之前就被拦下。[事实] 校验失败由 `validation_exception_handler` 统一转成 `Result`，前端拿到的是中文提示而不是 422 堆栈。
4. **依赖注入（Depends）适配本项目**：本系统几乎每个接口都要做三件重复的事——拿数据库会话、校验登录、校验模块权限。FastAPI 用依赖注入把这三种"横切关注点"写成可复用的依赖：[事实] `app/core/deps.py` 的 `get_current_user`、`app/core/perms.py` 的 `require_perms("animal")`，路由函数里一行 `Depends(...)` 搞定，路由体只写业务。在 Django 里要靠 middleware + decorator + DRF `permission_classes` 三处拼。
5. **性能与并发模型**：FastAPI 基于 ASGI（异步）标准，Django 传统上是 WSGI（同步）。本系统接口以数据库 I/O 等待为主，ASGI 在同等资源下更能扛并发。

**必须主动承认的一点（很重要）**

> "不过要说明的是，本项目**并不是全链路异步**——数据库层用的是同步 SQLAlchemy + PyMySQL，接口函数大多写成 `def`，由 FastAPI 自动丢进线程池执行。所以选 FastAPI 的**主要理由是轻量、类型安全、文档自动生成和依赖注入**，性能是"顺带的好处"而不是决定性理由。如果老师追问，我会如实这么讲。"

这段话会让评委觉得你**知道自己选了什么**，而不是跟风。

**预判追问**

| 老师追问 | 应答 |
| --- | --- |
| "那和 Flask 比呢？" | Flask 是 WSGI 微框架，校验、文档、依赖注入都要自己拼扩展（Marshmallow、flask-jwt、flask-restx）。FastAPI 相当于**把这一套现代组合开箱内置**了。 |
| "Django 自带 Admin，开发不是更快吗？" | 本系统 13 类业务、多角色、多租户、还有审核流程，Admin 那套定制性不够，改起来比自己写更费劲。而且毕设的价值恰恰在于**自己实现后端**，用 Admin 等于把主要工作量交给了框架。 |
| "Django 也有 DRF，为什么不选成熟的？" | DRF 成熟但抽象层多（View/Serializer/Permission/Throttle），学习与排错成本高；本项目接口形态高度一致（CRUD + 状态流转 + 分页筛选），FastAPI 的写法更直接。 |
| "为什么不用 SQLModel（Pydantic + SQLAlchemy 合体）？" | SQLModel 省事，但成熟度与生态不如直接用 SQLAlchemy 2.0，且把"数据校验"和"持久化"两个关注点耦合在一起，本项目需要 DTO 与 ORM 模型分开（见 4.3 四层分层）。 |

### 2.2 为什么用 SQLAlchemy 而不是 Django ORM / 手写 SQL？

- **对比裸 SQL**：13 个模块、几十张表、多条件筛选 + 分页，手写 SQL 拼字符串既容易出错又是**SQL 注入**的温床。ORM 的参数化查询天然防注入。**但不排斥原生 SQL**：[事实] 代码里确实保留了 `text()` 原生 SQL 兜底——`app/main.py` 的轻量迁移（补列、回填存量数据）和复杂统计就用了原生 SQL。**该用 ORM 用 ORM，该写 SQL 写 SQL**，这是务实做法。
- **对比 Django ORM**：Django ORM 与框架强绑定，而 SQLAlchemy 是**独立 ORM**，这本身也是"选 FastAPI 的加分项"——持久化层不被 Web 框架绑架，将来换框架不用重写模型。
- **SQLAlchemy 2.0 风格**：全面类型化（`Mapped[...]` 注解），IDE 能提示字段、能静态检查。

**预判追问**："N+1 查询你考虑过吗？" → 承认这是 ORM 的经典陷阱，本项目列表页用**显式 join / 分页查询对象**（每个模块有独立的 `XxxQuery` 模型）控制，避免逐行懒加载；如果将来出现慢查询，用 `DB_ECHO` 打开 SQL 日志定位。[事实] `app/config.py` 里的 `DB_ECHO` 开关就是为这个准备的。

### 2.3 为什么用 MySQL 而不是 PostgreSQL / SQLite / MongoDB？

| 候选 | 为什么没选 | 备注 |
| --- | --- | --- |
| **PostgreSQL** | 技术能力更强（JSONB、窗口函数、更严格的类型），但本系统没有非它不可的需求；而 MySQL 在学校环境、同学熟悉度、云端一键部署上更占优 | [取舍] 如果重做且需要复杂分析查询，我会考虑 PG |
| **SQLite** | 不适合多用户并发写（**但它在项目里有用**：见下） | [事实] 自动化测试用 SQLite 内存库 |
| **MongoDB** | 本系统是**强关系型**业务：圈舍→畜禽→饲喂→审核→库存→出栏，处处是外键与事务一致性要求，文档库不合适 | — |

**这里有一个加分点，一定要讲**：SQLite 在本项目里扮演了正确的角色——[事实] `livestock_server/tests/conftest.py` 用**SQLite 内存库**跑自动化测试，快、可重复、绝不污染开发/生产库。但我明确知道 **SQLite 无法代表 MySQL 的并发语义**，所以真并发用例（行锁、超卖）单独放在 `tests/test_concurrency_mysql.py`，必须显式指定 `TEST_MYSQL_URL` 才运行、默认跳过。[事实] 这个文件里的注释明确写了"严禁指向开发/生产库"。

> 这句话的价值：它证明你不是"随手拿测试库跑通就算"，而是**知道自己测的边界在哪**。

### 2.4 为什么用 JWT 而不是 Session？

- **前后端分离是前提**：Session 靠 Cookie + 服务端会话存储，跨域下要处理 Cookie 的 SameSite、跨站携带问题；JWT 把状态放在客户端，服务端无状态，请求头带 `Authorization: Bearer <token>` 即可。
- **服务端无状态 → 好扩展**：将来多实例部署不需要"粘性会话"或共享 Session 存储。
- **代价必须承认**：JWT **不能主动失效**（签发后在有效期内一直有效）、**续期麻烦**、**payload 是 Base64 明文**（不能放敏感信息）。
  本项目的折中：[事实] token 有效期设 1440 分钟（24 小时，`JWT_ACCESS_TOKEN_EXPIRE_MINUTES`）；`get_current_user` **每次请求都回库查用户并校验 `status != 1` 就报"账号已被禁用"**——这弥补了"无法撤销"的一部分问题（禁用账号可立即生效），但**不是**真正的 token 撤销机制。
- **被追问"用户登出怎么办 / token 被盗怎么办"**：如实答——当前"登出"只是前端删除本地 token，服务端没有黑名单；如果要做，标准做法是**在 Redis 里存 `jti` 黑名单直到 token 过期**（Redis 依赖已声明，见第 6 章）。

### 2.5 为什么密码用 bcrypt 而不是 MD5 / SHA-256？

- **本质区别**：MD5/SHA 是**快哈希**，设计目标是"算得快"，用于校验数据完整性；存密码需要**慢哈希**，让暴力破解的每次尝试都变贵。bcrypt 就是专为密码设计的慢哈希，**自带随机盐**（防彩虹表）、**cost 因子可调**（算力提升时可增大）。
- **实现细节（被追问时能加分）**：[事实] `app/core/security.py` 里用 `bcrypt.gensalt()` 生成盐、`bcrypt.hashpw()` 存哈希；因为 bcrypt 有 **72 字节输入上限**，代码里统一做了 `[:72]` 截断处理，避免超长密码直接抛异常。

---

### 2.6 为什么用 Pydantic 做校验？

- **一处声明，三处受益**：字段类型/范围/必填声明一次 → ① 请求进来时自动校验；② 返回出去时自动序列化（`model_validate`）；③ 自动生成 Swagger 文档的请求/响应 schema。
- **Pydantic v2 换了 Rust 内核**（pydantic-core），校验速度比 v1 有量级提升。
- [事实] 每个业务模块都有独立的 `schema.py`，里面区分**入参模型**（如 `AnimalIndividualIn`）、**出参模型**（`AnimalOut`）、**查询模型**（`AnimalQuery`）——这就是四层分层里的 DTO 层。

---

### 2.7 为什么用 APScheduler 而不是 Celery？

- **需求决定**：本项目只需要 4 个**每日定时任务**——[事实] `app/scheduler.py`：00:05 刷新生长阶段、00:10 生成繁育预警、00:20 刷新库存过期/缺货状态、00:30 清理 180 天前的档案历史。
- **Celery 的成本**：需要 broker（Redis/RabbitMQ）+ 独立 worker 进程 + 结果后端，运维担子立刻变重；为了 4 个 cron 任务引入消息队列，属于**杀鸡用牛刀**。
- **APScheduler 的优势**：进程内运行，`add_job(..., 'cron', ...)` 装完就用，`replace_existing=True` 保证幂等，跟着应用生命周期在 `lifespan` 里启停。

**[短板] 必须自己说出来**：APScheduler 跑在应用进程内，**多实例部署时每个进程都会跑一遍，任务会重复执行**；进程崩溃时任务不保证执行。改进方向：用 Redis 分布式锁包一层（`/健康检查接口`），或换成 Celery Beat / 独立调度服务。**老师很可能会问"你部署多台怎么办"，这题不答是失分，主动答是加分。**

## 第 3 章 前端选型：逐个回答"为什么不用 X"

### 3.1 为什么用 Vue 3 而不是 React？

> **先说结论，并且不要说"Vue 比 React 好"**——技术选型没有绝对优劣，只有适配度。

1. **学习曲线与可读性**：单文件组件（SFC）把模板、逻辑、样式放在一个 `.vue` 文件里，一个页面一眼看到全貌，这对一个 48 条路由的中后台系统意味着**极低的维护成本**。React 的 JSX 把结构揉进函数，自由度更高但心智负担更重。
2. **中后台生态**：Vue 侧的 Element Plus 是国内管理系统事实标准，表格、表单校验、分页、弹窗、日期选择全覆盖，中文文档完整，省掉大量自研组件的工期。
3. **熟悉度就是生产力**：在功能量固定的前提下，选自己熟练的技术栈能把时间花在业务上而不是查文档上。这是**工程上完全正当的选型依据**。

**预判追问**："React 生态不是更大吗？" → 承认是的，React 生态更大、招人更容易、跨端方案（RN）更成熟；但本项目的约束是**单人 + 有限工期 + 中后台形态**，在这个约束下 Vue 的投入产出比更高。

---

### 3.2 为什么用 Element Plus？

- 中后台组件覆盖最全，且**中文文档**降低查文档成本。
- **按需引入**做得干净：[事实] `vite.config.ts` 用 `unplugin-auto-import` + `unplugin-vue-components` 配 `ElementPlusResolver`，组件和样式都按需编译，不用全量引入。
- **这里有一个可以讲的工程细节（答辩加分项）**：按需引入会产生 `element-plus/es/components/<name>/style/css` 这类深层导入，Vite 启动时扫描不到，页面第一次用到某个组件时会"现场发现依赖 → 重新预构建 → 整页刷新"，表现就是**开发时点菜单会卡一下/闪一下**。我的解法是在 `optimizeDeps.include` 里**枚举磁盘上真实存在的组件样式文件**（而不是写通配符，因为通配符在文件系统展开时匹配不到 `css.mjs`），启动时一次性预构建完。

> 这类细节能证明你不是"配完能跑就行"，而是**追到过根因**。但注意：讲这个之前要先确认老师感兴趣，别一上来就深入。

### 3.3 为什么用 Vite 而不是 Webpack？

- **开发期速度**：Vite 用 esbuild 预构建第三方依赖 + 浏览器原生 ESM 按需加载，冷启动和热更新速度跟 Webpack 不是一个量级；项目越大差距越明显。
- **生产期**：用 Rollup 打包，配置比 Webpack 简洁得多（本项目 `vite.config.ts` 一个文件搞定插件、别名、代理、测试环境配置）。
- **顺手的好处**：开发代理一并搞定，[事实] `server.proxy` 把 `/api` 转发到 `http://127.0.0.1:8000`，前端开发时不存在跨域问题。

---

### 3.4 为什么用 Pinia 而不是 Vuex？

- Vue 官方新一代状态管理，**TS 类型推断自然**（不需要为每个 mutation 手写类型），也**没有 mutations 那层样板代码**。
- **按需使用**：本项目的全局状态其实很少——[事实] `src/stores/` 下只有一个 `auth.ts`（当前用户、权限、超管选中的养殖场）。页面级数据用 `composables/usePagedList.ts` 这类组合式函数管理，**没有为了"用状态管理"而把所有东西塞进 store**。

> 这句话是有意说的：**状态管理的反模式是把页面数据也放全局**。我说清边界，说明我懂它的适用范围。

---

### 3.5 Axios 拦截器做了什么？（这题经常被问，因为它是"前后端约定"的落地处）

[事实] `src/api/request.ts` 里三个动作，都值得说：

1. **统一注入身份**：请求拦截器从本地读 token → `Authorization: Bearer <token>`；如果 JWT 里 `user_type === 1`（超管），再自动附加 `X-Farm-Id` 头，用于切换养殖场。
2. **GET 请求竞态防护**：同一接口的 GET 请求连发时**只认最后一次**——给每个请求打自增 `seq`，回来的响应如果 `seq` 不是最新，就直接静默丢弃。解决的是**"快速切畜种/连续点查询/翻页时，旧慢请求后到把新结果覆盖掉"**的数据闪回问题。POST/PUT/DELETE 不做这个处理（用户主动提交不能丢）。
3. **统一响应处理**：因为后端 HTTP 恒返回 200、靠业务 `code` 区分，前端只需在响应拦截器里判断一次 `code`，按 `401 / 403xx / 500` 统一弹提示、跳登录。

## 第 4 章 架构层面的"为什么"（老师更爱问这些）

### 4.1 统一响应格式：为什么所有接口 HTTP 都返回 200？

[事实] `app/core/response.py` 定义了统一结构：

```json
{ "code": 200, "msg": "success", "data": {}, "timestamp": 1730000000 }
```

`app/core/exceptions.py` 里三个异常处理器（业务异常 / 参数校验异常 / 兜底异常）**全部 `status_code=200`**，靠 body 里的 `code` 区分成败。

**为什么这么做**
- 前端只需要**一套拦截器**判断 `code`，不用同时处理 HTTP 状态码和业务码两套逻辑。
- 错误码可以自定义分类：`400` 参数错误、`401` 未登录/禁用、`40300` 未关联养殖场、`40302` 超管农场上下文错误、`40303` 无模块权限、`500` 系统错误。业务错误可以用自己的号段。
- 兜底处理器会把真实堆栈写进日志、**只给前端返回"服务器内部错误"**，不泄露实现细节。

**[取舍] 必须承认的代价（被追问时正面答）**
- **不符合 REST 语义**，网关/负载均衡/监控无法靠状态码做重试与告警策略；
- Swagger 里所有接口的响应都是 200，**看不出真实错误**；
- 与"HTTP 状态码表达语义"的最佳实践相悖。

**标准答法**："这是与企业内部接口规范对齐的**主动取舍**——我把它集中放在三个异常处理器里，业务代码只需 `raise BizException('耳标已存在', code=40001)`，不用层层 try/except。如果重做，我会把 HTTP 状态码用起来，业务码只承载更细的语义。"

---

### 4.2 四层分层：model / schema / service / api

[事实] 每个业务模块都是固定四件套：

| 层 | 文件 | 职责 | 纪律 |
| --- | --- | --- | --- |
| Model | `model.py` | ORM 表结构 | 不写业务逻辑 |
| Schema | `schema.py` | DTO：入参 / 出参 / 查询对象 | 不碰数据库 |
| Service | `service.py` | 业务逻辑、事务 | 不感知 HTTP |
| API | `api.py` | 路由、参数、依赖注入 | 不写业务 |

**好处**：职责单一、`service` 层可以脱离 HTTP 直接单测、将来换 Web 框架不影响业务层。
**代价（诚实）**：文件多，一个小需求的改动要动 4 个文件；对超小模块是过度设计。**在本项目 13 个模块的规模下，收益大于成本。**

**预判追问**："Service 层怎么保证不被绕过？" → 靠约定 + Code Review，本项目没有用架构测试工具强制（可以用 `import-linter` 之类的工具做分层约束，属于改进点）。

---

### 4.3 多租户：为什么用"单库共享表 + farm_id"而不是分库？

**三种方案我评估过**：

| 方案 | 隔离强度 | 成本 | 适用 |
| --- | --- | --- | --- |
| **单库共享表 + 租户 ID**（选了这个） | 中（靠代码保证） | 最低 | 租户多、单租户数据量小 ✅ |
| 每租户独立 schema | 较高 | 中 | 租户数量可控 |
| 每租户独立库 | 最高 | 高（连接池、迁移、备份都要按租户做） | 大客户、强合规 |

**为什么选共享表**：中小养殖场数量多、**单个养殖场的数据量很小**（几千头畜禽、几万条记录），共享表 + `farm_id` 过滤是最经济的选择；分库分表在这个体量下纯属自找麻烦。

**怎么防越权（这块一定要讲，老师会追问"那你不怕串数据？"）**
1. **所有查询强制带 farm_id**：每个 service 方法的签名里都有 `farm_id` 参数，从依赖注入传进来，而不是在方法内部临时取。
2. **普通用户伪造请求头无效**：[事实] `resolve_farm_id()` 里，`user_type` 为 2/3 的用户**直接忽略 `X-Farm-Id`，只用自己账号上的 `farm_id`**——防止普通员工改个请求头去看别的养殖场的数据。
3. **超管必须显式指定且严格校验**：[事实] 超管（`user_type=1`）没有 `farm_id`，必须通过 `X-Farm-Id` 指定目标养殖场；该 ID **必须指向存在且未删除的养殖场**，否则直接抛 `40302` 错误，**绝不静默回退到"第一个养殖场"**。缺失时也报错要求先选择。
4. **这个"不回退"是有意为之**：[事实] `tests/test_farm_context.py` 有 7 个用例专门盯这个行为——超管没传、传了不存在的、传了已删除的、传了非法值、普通用户试图用请求头切换租户，**全部必须报错**。

**这句总结很值钱**："超管切换养殖场我最初是允许回退到默认农场的，后来改成**严格失败**——因为静默回退会导致'我以为在看 A 场，实际操作的是 B 场'，这种错误在多租户系统里是**灾难性的数据事故**，宁可报错也不能猜。"

### 4.4 审核状态机：为什么不用工作流引擎？

- **需求很简单**：饲喂、进货、领用、防疫、诊疗、配种六类业务，都是**"员工提交 → 待审核 → 场主通过/驳回"**的一步审批。
- **设计**：[事实] 状态直接落在各业务表的 `audit_status` 字段（`待审核` / `通过` / `驳回`），**不新增审核表**。`app/modules/review/` 只做两件事：**聚合查询**六类待审核记录（统一成 `ReviewItemOut`）、**转发**审核动作给对应模块的 service。这样审核中心不持有业务状态，避免"两处状态不一致"。
- **为什么不上 Activiti/Flowable**：工作流引擎是为**多级审批、会签、动态流程图**设计的，本系统是一步审批，引入引擎等于把简单问题复杂化——多一个中间件、多一套模型、多一份学习成本。

**预判追问**："那如果要做多级审批呢？" → 扩展路径是给业务表加 `audit_level` 字段，或抽一张 `audit_flow` 表；当流程复杂度真的上来（会签、条件分支、可配置流程）时再考虑引擎。**架构跟着复杂度长，不预支。**

---

### 4.5 并发安全：库存会不会超卖 / 会不会被重复审核？

这是**技术上最有分量的一问**，要答得具体：

- **问题场景**：领用审核通过时要扣减库存。如果两个人同时审核、或重复点击，可能出现"库存扣两次"或"库存被扣成负数"。
- **[事实] 解法**：`app/modules/inventory/service.py` 里审核时先用 `with_for_update()` 对库存行加**悲观锁**，并校验记录当前状态必须是"待审核"（`if p.audit_status != "待审核"` 直接拒绝），再改库存、同一事务提交。行锁保证串行化，状态校验保证**幂等**（重复审核直接拒绝，不会重复扣减）。
- **[事实] 怎么验证**：`tests/test_concurrency_mysql.py` 三个真并发用例——并发双审只生效一次、并发领用不超库存、并发进货不重复不丢失。**必须用真 MySQL 跑**（SQLite 不支持这种并发语义，所以默认跳过）。
- **被追问"为什么不乐观锁"**：乐观锁（版本号）在本场景会因冲突重试而失败率偏高；库存扣减是**短事务 + 热点行**，悲观锁更直接。也可以比较：Redis 预扣减适合超高并发，本系统体量不到。

---

### 4.6 权限模型：三道关卡

[事实] 一次请求要过三关：

| 关卡 | 实现 | 拦什么 |
| --- | --- | --- |
| ① 身份 | `get_current_user`：解析 JWT → 查库 → 校验 `status == 1` | 未登录、token 失效、账号被禁用 |
| ② 模块权限（RBAC） | `require_perms("feeding")`：查用户角色 → `sys_role.perms` | 员工岗位没配这个模块就不能访问 |
| ③ 数据范围 | `resolve_farm_id()`：普通用户锁死自己的 farm_id | 跨租户越权 |

**实现细节**：[事实] `require_perms` 写成**路由级依赖**（如 `APIRouter(dependencies=[Depends(require_perms("animal"))])`），挂在 router 上，该模块所有接口自动生效，新增接口不会漏配。超管/场主默认拥有全部模块权限，不受角色配置限制。

### 4.7 其他值得记住的架构点

| 点 | 内容 |
| --- | --- |
| **操作日志** | [事实] `oper_log_middleware` 拦截 POST/PUT/DELETE，记录操作人、URL、中文操作名、结果到 `oper_log` 表。**技术细节**：中间件里显式读出并缓存响应体后再回放——因为流式响应没有 `.body`，原实现恒取到 `None`，导致所有日志一律记成功；同时把同步写库丢进 `run_in_threadpool`，避免阻塞事件循环 |
| **数据库自迁移** | [事实] `app/main.py` 的 `init_db()` 启动时 `create_all` 建表 + 依次执行 `_ensure_*` 轻量迁移（补 `sys_role.perms`、`material_stock.unit_price`、`sys_notice.farm_id`、`pen_info.species`、`mating_record.audit_status`），含存量数据回填 |
| **配置安全兜底** | [事实] `app/config.py` 里若 `JWT_SECRET_KEY` 仍是 `.env.example` 的默认占位串，**应用直接拒绝启动**（占位串是公开的，知道它就能伪造任意用户 token） |
| **连接池** | [事实] `pool_pre_ping=True`（取连接前先探活）+ `pool_recycle=3600`（避免 MySQL 8 小时空闲断连） + `pool_size=10 / max_overflow=20` |
| **CORS** | [事实] 开发期用 `allow_origin_regex` 放行 `localhost/127.0.0.1` 任意端口（Vite 端口被占用会自动递增，写死 5173 会失败），生产通过 `CORS_ORIGINS` 环境变量追加正式域名 |

### B 档：架构设计类

**B1 ★ 你这个系统最核心的设计是什么？**
→ **统一审核状态机**。六类业务（饲喂/进货/领用/防疫/诊疗/配种）共用同一套"提交→待审核→通过/驳回"语义，状态落在各自业务表、审核中心只做聚合与转发。好处是**业务状态单一来源**（不存在"审核表说通过了、业务表还是待审核"），且新增一类待审核业务只需加一次映射、不改造审核中心。

**B2 ★ 多租户怎么实现的？数据会不会串？**
→ 见 [4.3](#43-多租户为什么用单库共享表--farm_id-而不是分库)。重点讲三个防线 + "严格失败不回退"的设计意图。

**B3 为什么分四层？会不会过度设计？**
→ 见 [4.2](#42-四层分层model--schema--service--api)。**主动承认**：小模块确实啰嗦，13 个模块规模下收益大于成本。

**B4 为什么要做审核流程？员工不能直接改数据吗？**
→ 业务合理性：养殖场是**"员工执行、场主负责"**的组织形态。饲喂、防疫、领用这些记录直接影响成本核算和防疫合规，必须由场主确认；同时审核通过才触发库存扣减/母猪置妊娠等副作用，**保证数据变更都在有权限的人确认后发生**。
追问"所有操作都要审核吗" → 不是，[事实] 管理端增加库存就是免审的（落一条"通过"状态的进货记录作为同步依据）。

**B5 为什么不做微服务？**
→ 规模决定架构：一个业务域、一个团队、数据强一致需求明确。微服务会带来分布式事务、服务发现、链路追踪、独立部署的运维成本，**在本项目里收益为负**。单体的边界：13 个模块**已经按限界上下文分包**，将来真需要拆，模块边界就是拆分点。

**B6 前后端怎么协作的？接口怎么对？**
→ 后端启动即有 Swagger（`/docs`），接口文档（`docs/API-智能养殖信息管理系统.md`，5000+ 行）作为契约；统一响应格式让前端只需要一套拦截器；开发期 Vite 代理转发 `/api` 到 8000 端口，不存在跨域。

**B7 你的系统"智能"体现在哪？（题目里有"智能"二字，一定会被问）**
→ 说实话：系统里的"智能"不是 AI，而是**业务规则的自动化**——
① **耳标自动生成**（畜种位 + 圈舍编号 2 位 + 序号 2 位，共 5 位，空号复用，转圈舍自动重生成）；
② **生长阶段自动判定**（按出生日龄 + 牛/羊/猪三套配置，每日定时刷新）；
③ **繁育预警自动生成**（配种满 60 天未孕检 → 孕检提醒；预产期前 15 天 → 临产提醒；产犊满 60 天未配种 → 未发情提醒）；
④ **预产期自动计算**（牛 280 / 羊 150 / 猪 114 天）；
⑤ **成本自动分摊**（饲料成本按圈舍在栏头数分摊，售出时按份额结转）。
⚠️ 雷区：**不要说"用了人工智能/机器学习"**——代码里没有，一问就穿。要用"业务规则引擎/自动化决策"这个词。

### C 档：安全类

**C1 ★ 你的系统安全上做了哪些考虑？**
→ 按五层答：
① **密码**：bcrypt 慢哈希 + 随机盐，永不存明文；
② **鉴权**：JWT + 每次请求校验用户状态（禁用账号立即失效）；
③ **越权**：RBAC 模块权限 + 租户数据隔离（`X-Farm-Id` 严格校验、普通用户伪造无效）；
④ **注入**：ORM 参数化查询；**XSS**：Vue 模板默认转义；
⑤ **配置**：JWT 密钥若为默认占位串**拒绝启动**；全局异常处理器不向前端泄露堆栈。
**然后主动说短板**：无 token 黑名单、无接口限流、无验证码；生产环境必须配 HTTPS（反向代理层做）。

**C2 token 泄露了怎么办？登出怎么实现？**
→ 现状：登出只是前端删 token，服务端没有失效机制（因为 JWT 无状态）。
改进：Redis 存 `jti` 黑名单，校验时比对；或改用**短期 access token + refresh token**。⚠️ 不要答"JWT 本身很安全所以不怕泄露"。

**C3 你怎么防 SQL 注入？**
→ ORM 参数化；[事实] 仅有的 `text()` 原生 SQL 用在**迁移脚本里**（DDL 与存量回填），参数是代码内常量、不接受用户输入，所以没有注入面。**这句话是关键**——承认用了原生 SQL 但说清为什么这里没有注入风险。

**C4 密码为什么加盐？盐存在哪？**
→ 防彩虹表（相同密码得到不同哈希）。bcrypt 把**盐和哈希编码在同一个字符串里**（`$2b$12$...`），不需要单独字段存储。

**C5 普通员工能不能看到别的养殖场的数据？**
→ 不能。① 所有查询强制带 farm_id；② 普通用户传 `X-Farm-Id` 会被**忽略**（不是校验通过，是直接不用）；[事实] `test_farm_context.py::test_normal_user_cannot_switch_farm_via_header` 专门测这个。

### D 档：性能 / 并发 / 扩展类

**D1 ★ 库存会被扣成负数吗？并发审核怎么办？**
→ 见 [4.5](#45-并发安全库存会不会超卖--会不会被重复审核)。行锁 + 状态幂等校验 + 真 MySQL 并发测试。

**D2 系统能扛多少并发？**
→ **不要报一个假数字**。标准答法："单机 uvicorn 部署，数据库连接池 10+20。业务体量是单个养殖场几千头畜禽、几十个用户，**并发压力很低**，所以我没有做压测——如果要做，我会先用 Locust 跑出接口基线，再看瓶颈在数据库还是应用。"
⚠️ 雷区：不要编造 "支持 1000 并发" 这种没有依据的数字。承认"没测过"比编数字安全得多。

**D3 用户量上来了怎么扩展？**
→ 分四层答：
① **应用层**：JWT 无状态 → 直接加实例 + 负载均衡；
② **数据层**：加索引 → 读写分离 → 按 farm_id 分片；
③ **定时任务**：现在是单机进程内调度，**多实例前必须先加分布式锁或独立调度**（否则任务重复执行）；
④ **热点**：统计/大屏走缓存（Redis 依赖已声明，可作为落地起点）。

**D4 数据库慢查询怎么排查？**
→ [事实] 打开 `DB_ECHO` 打印实际执行的 SQL；MySQL 侧 `EXPLAIN` 看执行计划；本项目已在 `pen_info.species` 这类查询列上建索引。**索引不是无脑加**：写多读少的小表不加。

**D5 项目有什么性能优化？**
→ 老实讲几件真做过的：[事实] ① 前端 element-plus 按需引入 + ECharts 按需引入 + Vite `optimizeDeps` 预构建（消除开发期整页刷新）；② 后端连接池探活与回收；③ 统一响应体的日志中间件把同步写库放进线程池避免阻塞事件循环；④ DB_ECHO 默认关闭（曾因全量打印 SQL 导致 Windows 终端输出拖慢请求体感）。

### E 档：业务逻辑类

**E1 耳标怎么生成的？重复了怎么办？**
→ [事实] 规则：**畜种位 + 圈舍编号（2 位）+ 序号（2 位）共 5 位**；同一圈舍内序号自增，**空号复用**（删除后产生的号码会被新入场个体回收使用）；**转圈舍会重新生成耳标**（因为耳标里含圈舍编号）。删除是软删除，档案历史保留 180 天后由定时任务清理。
追问"为什么不用 UUID" → 耳标要**人可读、可现场核对**，UUID 现场没法用。

**E2 生长阶段怎么判定？**
→ 按**出生日龄 + 畜种**查配置表（牛/羊/猪三套阶段划分），每日 00:05 定时刷新；妊娠阶段是由配种记录标记的，**定时任务不覆盖"妊娠"状态**。

**E3 预产期怎么算？**
→ 配种日期 + 妊娠期：**牛 280 天 / 羊 150 天 / 猪 114 天**，记录审核通过后写入 `expected_birth_date`。

**E4 ★ 成本是怎么分摊的？（这题最能体现工作量）**
→ 场景：一个圈舍里的畜禽吃同批饲料，怎么算"单只成本"、卖出去时怎么结转？
做法：饲料成本记录在**圈舍 + 时间段**上，按该时间段内圈舍的**在栏头数**分摊到每头；出栏销售时按该个体的份额结转成本。**难点是边界**——中途转圈舍、部分出栏、跨圈舍混养、时间窗口恰好为空，都会导致重复计算或漏算。[事实] `tests/test_feeding_cost_allocation.py` 有 5 个用例专门覆盖：不重复计数、出栏明细按圈舍份额分摊、部分出栏与跨圈舍不串账、转圈前的早期记录不归属新圈舍、空圈舍与零长度窗口不报错。
**这句总结很值钱**："成本分摊看起来是除法，实际是**时间窗口 + 归属关系**的问题，我是先把边界用例写成测试，再实现逻辑的。"

**E5 库存成本怎么算的？**
→ [事实] 库存行上存 `unit_price`（均价快照），领用时把当时的单价**快照到领用记录**上，这样**历史成本不会因为后续进货价变化而被改写**。管理端可免审直接增加库存（落一条"通过"状态的进货记录作为同步依据）。

**E6 字典表是干什么的？为什么不用枚举写死？**
→ [事实] 预置 13 类 57 条业务字典（供品种、疫苗类型、饲料类型等下拉使用）。**枚举写死意味着改一个下拉选项要改代码 + 重新发版**；字典是数据，改配置即可。疫苗类型还做了**白名单校验**，防止随便录入。这是"**留扩展口**"的设计。

### F 档：刁钻 / 压力类

**F1 ★ 你这个系统有什么创新点？**
→ **不要吹"创新"大词，讲清楚四件"完整性"上的贡献**：
① **全流程闭环**：市面很多养殖系统只做档案或只做饲喂，本系统把"入栏→饲喂→防疫→繁育→审核→库存→出栏"打通，且用**同一套审核状态机**贯穿；
② **多租户 SaaS 形态**：一份部署服务多个养殖场，数据严格隔离，这在毕设层面属于进阶设计；
③ **业务规则自动化**：耳标生成、生长阶段、繁育预警、成本分摊，把"人算"变成"系统算"；
④ **工程完备性**：统一响应/异常/操作日志/RBAC/租户隔离/自动化测试（含真并发用例）——**不是 Demo，是一个具备工程规范的系统**。

**F2 ★ 你的工作量体现在哪？**
→ 用第 0 章那张表：159 个接口、13 个模块、48 条前端路由、5000+ 行接口文档、13 类 57 条字典、4 个定时任务、22 个后端测试（含 3 个真 MySQL 并发用例）+ 3 个前端测试。然后补一句："**其中审核状态机、库存审核并发、成本分摊三块是我花时间最多的地方**。"

**F3 ★ 如果重做一次，你会改什么？（必问题，答得好非常加分）**
→ 五条，按优先级：
① **数据库迁移**：现在靠 `create_all` + 手写 `_ensure_*` 补列，属于应急手段；应统一到 Alembic（当前只有一个 baseline revision）；
② **错误处理规范化**：把 HTTP 状态码用起来，业务码承载更细语义；
③ **定时任务分布式化**：加分布式锁，否则多实例部署会重复执行；
④ **安全补强**：token 黑名单（Redis）、接口限流、生产 HTTPS；
⑤ **工程化**：补 Docker 镜像与 CI（当前没有 Dockerfile / CI 配置，测试已经能返回非零退出码，**具备接入 CI 的条件**）。

**F4 系统有什么不足 / 局限？**
→ 同 F3，但要加**业务局限**：无移动端、无离线能力、报表维度偏基础、没有对接硬件（称重/环境传感器）。**主动承认局限比被问出来强。**

**F5 你这些代码都是自己写的吗？**
→ 如实回答。毕设答辩很在意这个。**诚实 + 能讲清设计决策 = 最强的答案**。如果用了 AI 辅助或参考了开源，就说清"哪部分是参考、哪部分是自己设计、为什么这么设计"——因为**评委要考的是你是否理解**，第 5 章这些"取舍理由"就是你的底气。

**F6 为什么这个题目有市场？做给谁用？**
→ 目标用户：**中小型养殖场**（几十到几千头规模），他们普遍还在用 Excel 甚至纸质记录，痛点是**账对不上、防疫漏打、成本说不清、多场管理混乱**。本系统把这几件事结构化，且**一个实例可服务多个养殖场**，天然适合 SaaS 化交付。
