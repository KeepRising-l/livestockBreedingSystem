## 进入系统管理

1. 用超级管理员账号登录系统（如 `admin`）。
2. 点击左上角「系统管理」一级菜单，展开后有 6 个子项：用户管理、角色管理、菜单管理、字典管理、日志管理、通知公告。
3. 点进任一子项即可进入对应管理页。

> ⚠️ 只有 `user_type = 1`（超级管理员）能看到并操作系统管理。
> 养殖场主（`user_type=2`）和员工（`user_type=3`）在侧边栏**看不到**这个入口。

## 用户管理

> 页面路径：`系统管理 → 用户管理`（路由 `/system/user`）
> 作用：管理**所有**登录账号（超级管理员 / 养殖场主 / 员工）。是全局唯一的用户入口，养殖场主开员工的窗口在 `养殖场管理 → 员工管理`，但超管在这里统一管理所有人。

### 功能清单

| 功能 | 说明 |
| --- | --- |
| 列表筛选 | 按账号 / 姓名 / 手机号 / 用户类型 / 所属养殖场 / 状态 查询 |
| 新增用户 | 创建任意类型的账号 |
| 编辑用户 | 改姓名、电话、用户类型、所属养殖场、岗位、状态 |
| 重置密码 | 把某账号密码重置为指定值（常用于员工忘记密码） |
| 分配角色 | 给用户勾选担任的角色（如「兽医」「饲喂员」），决定其业务模块权限 |
| 禁用 / 启用 | 把账号 status 置 0 停用，该账号无法再登录 |
| 删除用户 | 逻辑删除（软删），超级管理员账号不允许删除 |

### 操作步骤

**新增用户**
1. 点「新增用户」。
2. 填写：账号（唯一）、密码、姓名、电话、用户类型（1 超管 / 2 场主 / 3 员工）、所属养殖场、岗位（员工）、状态。
   - 用户类型选「员工」时，系统会**按岗位自动关联一个默认角色**（如「兽医」→ vet 角色），无需手动赋权。
   - 若想给更精细的角色，可在保存后用「分配角色」覆盖。
3. 点「确定」保存。

**分配角色**
1. 在列表行点「分配角色」。
2. 勾选 1 个或多个角色，点「确定」。
3. 角色决定该用户能访问哪些业务模块（见[角色管理](#角色管理)）。

> 💡 员工登录后落地在「我的工作台」，其能看到哪些业务模块（圈舍/档案/饲喂/防疫…），由**角色的权限模块** `perms` 决定，并在前端 `Sidebar` 里按 `hasPerm(模块key)` 过滤渲染。

## 角色管理

> 页面路径：`系统管理 → 角色管理`（路由 `/system/role`）
> 作用：定义"角色 → 可访问哪些业务模块"的对应关系。角色是权限的载体，通过用户的「分配角色」挂到人身上。

### 预置角色
系统初始化时已内置 6 个角色：

| 角色名 | 角色标识(role_key) | 默认可访问模块 `perms` |
| --- | --- | --- |
| 超级管理员 | `admin` | 全部（含系统管理） |
| 养殖场主 | `owner` | 全部业务模块（不含系统管理） |
| 饲喂员 | `feeder` | dashboard, pen, animal, feeding |
| 兽医 | `vet` | dashboard, pen, animal, health, inventory |
| 繁育员 | `breeder` | dashboard, pen, animal, breeding |
| 库管员 | `keeper` | dashboard, pen, inventory |

> 全部业务模块 key：`dashboard farm pen animal feeding inventory health breeding review finance statistics`（另加 `system`）。

### 功能
| 功能 | 说明 |
| --- | --- |
| 列表 | 按角色名 / 状态查询 |
| 新增角色 | 自建角色，填名称、唯一标识、权限模块列表、排序、状态 |
| 编辑角色 | 修改名称、权限模块、排序、状态（**标识不可改**，或改了会做唯一性校验） |
| 删除角色 | 逻辑删除；**已分配给用户的角色不可删除** |

### 自定义一个岗位角色（示例：加一个"营养师"）
1. 点「新增角色」。
2. 名称填「营养师」，权限标识填 `nutritionist`。
3. 权限模块 `perms` 填 `["dashboard","pen","animal","feeding"]`（JSON 数组，勾选你想让它访问的模块）。
4. 保存后，在「用户管理 → 分配角色」里就能把这个角色挂给任意员工。

> ⚠️ **自定义角色的权限标识要能被前端识别**：前端 `Sidebar` 是硬编码的模块模板 + `hasPerm(模块key)` 过滤。你自建的 `perms` 数组里的模块 key，只有落在上面列的业务模块 key 集合里才会真正控制菜单显示。纯粹自造的 key（如 `nutritionist`）写进角色后，前端没有对应菜单项去消费它——不报错，但也不产生可见效果。

## 菜单管理（专题详解）

> 页面路径：`系统管理 → 菜单管理`（路由 `/system/menu`）
> 作用：维护一张**目录 / 菜单 / 按钮**的层级树。它既做 RBAC 的"权限项"登记，也用于后端 `/auth/permissions` 返回"当前用户可见菜单"，给前端做**预留的菜单渲染数据**。

### ⚠️ 最重要的现状提醒（先读这段，避免白折腾）

**当前前端侧边栏并不读取这张菜单表。**

左侧导航栏实际上由 `livestock-web/src/layouts/components/Sidebar.vue` 里的**写死的 `MODULES` 数组**（圈舍/档案/饲喂…）加上 RBAC 权限模块过滤动态生成的；`sys_menu` 表现在**不驱动**侧边栏显示。

反过来讲：
- 你在这张菜单管理里**新增/编辑/删除**，侧边栏**不会跟着变**，页面能否访问仍由 `Sidebar` 硬编码 + 用户角色 `perms` 控制。
- 后端 `get_user_menus` 照常算，并在 `/auth/permissions` 的响应里返回 `menus` 字段，只是前端暂未消费它做菜单渲染。

因此这张表现在的定位是：**RBAC 菜单/权限的“标准登记表”**。实操上建议把它当作一个**权限字典/审计台账**来维护（菜单要规范、标识要对齐数据表），而不要指望它改侧边栏；等以后需要动态菜单时，这棵树的字段结构已经完全就绪。

### 树的结构：三层类型

菜单用 `parent_id` 组成树形，每层用 `menu_type` 标识：

| menu_type | 含义 | 典型字段 | 例子 |
| --- | --- | --- | --- |
| `M` 目录 | 顶级分组，用于收纳子菜单 | path（可空）、icon | 「数据大屏」「养殖场管理」「系统管理」 |
| `C` 菜单 | 一个可点击进入的**页面** | path、component、perms | 「用户管理」→ path=`user`、component=`system/UserList` |
| `F` 按钮 | 页面内的操作权限位 | perms | 「新增用户」→ perms=`system:user:add` |

> 权限标识 `perms` 的建议命名规范：`模块:子功能:动作`，如 `system:user:add`、`animal:record:delete`。
> 前端 `Sidebar` 目前用**模块级 key**（如 `animal`）做 hasPerm，而这张菜单表里既可以登记模块级（`perms=animal`）也可以登记更细的动作级（`perms=animal:record:delete`），两种粒度并存互不冲突。

### 操作步骤

**新增顶级目录**
1. 点「新增菜单」。
2. 上级菜单**不选**（或选「顶级菜单」）→ 即为顶级。
3. 菜单类型选「目录 M」，填菜单名称（如「设置中心」）、图标（如 `Setting`）、显示顺序。
4. 保存。

**新增子菜单（页面）**
1. 在对应目录行的操作列点「新增下级」。
2. 菜单类型选「菜单 C」，上级菜单会自动带出该目录。
3. 填：菜单名称、路由地址 `path`（如 `user`）、组件路径 `component`（如 `system/UserList`）、权限标识 `perms`（如 `system:user:list`）、图标、排序、显示/状态。
4. 保存。

**新增按钮（权限位）**
1. 在菜单行点「新增下级」。
2. 菜单类型选「按钮 F」，填菜单名称 + 权限标识（如「新增用户」→ `system:user:add`）。
3. 按钮不需要填路由地址/组件路径（前端按 `menu_type !== 'F'` 才显示这两项）。

**编辑 / 删除**
- 编辑：任意行点「编辑」，改字段。注意：**父菜单不能选成自己**，否则后端拒绝（code 40047）。
- 删除：点「删除」；**若该菜单下还有子菜单，会要求先删子菜单**（code 40048），避免产生孤儿节点。

### 字段速查

| 字段 | 说明 | 必填 |
| --- | --- | --- |
| 上级菜单 parent_id | 树形父节点，空为顶级 | - |
| 菜单类型 menu_type | M 目录 / C 菜单 / F 按钮 | ✅ |
| 菜单名称 menu_name | 显示名 | ✅ |
| 路由地址 path | C/M 用，如 `user`、`/system` | C 常用 |
| 组件路径 component | C 用，映射前端 view 文件 | C |
| 权限标识 perms | F 必填、C 常填 | F ✅ |
| 图标 icon | Element Plus 图标名，如 `Setting` | - |
| 排序 sort | 同级显示顺序，越小越靠前 | - |
| 显示状态 visible | 1 显示 / 0 隐藏 | - |
| 状态 status | 1 正常 / 0 停用 | - |

### 与"用户能看到什么菜单"的关系

最终"某用户登录后侧边栏有哪些菜单"= `Sidebar.vue` 硬编码模板 ∩ `该用户角色 perms`（hasPerm 过滤）∩ `用户类型可见性`（如 review/finance 仅场主+超管）。
菜单管理这张树，是这套规则之外的**数据层登记**，用于沉淀标准菜单清单和权限标识。维护好它，将来启用动态菜单时直接可用，且有利于权限设计与审计。

## 字典管理（专题详解）

> 页面路径：`系统管理 → 字典管理`（路由 `/system/dict`）
> 作用：维护系统里所有"枚举下拉框"的可选项。**这是 6 个功能里真正即时影响业务表单的一个**。左侧选「字典类型」，右侧维护该类型下的「字典数据」。

### 区分两个概念（务必分清）

| 概念 | 表 | 是什么 | 例 |
| --- | --- | --- | --- |
| **字典类型** dict_type | `sys_dict_type` | 一类下拉框的"类目"，有一个唯一标识 | `sys_breed`（品种）、`sys_vaccine_type`（疫苗类型） |
| **字典数据** dict_data | `sys_dict_data` | 该类型下的具体选项，一条就是一个下拉项 | 品种：黄牛/西门塔尔牛/…；疫苗：口蹄疫/布病/… |

> 结构一句话：**类型是"这张下拉框叫什么"，数据是"这一项里的一个选值"**。一个类型下挂多条数据，一条数据对应一个可选项。

### 页面布局
- **左栏（9/16）**：字典类型列表，含搜索框、状态、新增/编辑/删除。
- **右栏（15/16）**：当前选中类型下的字典数据列表，含搜索、新增/编辑/删除。
- 点击左侧某一行，右侧自动加载该类型的全部数据。

### 数据字段说明（重点看 dict_extra）
每条字典数据主要有 4 个字段 + 状态：

| 字段 | 说明 | 例 |
| --- | --- | --- |
| 标签 dict_label | 下拉框里**显示**的文本 | 黄牛 |
| 键值 dict_value | 存进数据库的**实际值** | 黄牛（此例标签=键值；有的类型标签与键值不同，如用户类型标签「超级管理员」键值 `1`） |
| 排序 dict_sort | 下拉顺序 | 1 |
| **扩展信息 dict_extra** | **一段 JSON**，用于给该项挂额外属性，业务代码按它做过滤/联动 | `{"species":"cattle"}` |
| 状态 status | 1 正常 / 0 停用（停用项不出现在业务下拉里） | 1 |

> `dict_extra` 是最关键也最易错的字段：它是 JSON **字符串**，业务代码会 `JSON.parse` 它。格式写坏（少花括号、无效 JSON）会导致该类型在下拉框里被过滤掉/不可选。

### 预置字典类型清单（系统首次启动自动生成 13 类）
| 类型标识 | 名称 | data 里 dict_extra 的作用 |
| --- | --- | --- |
| `sys_user_type` | 用户类型 | —— |
| `sys_post` | 岗位 | —— |
| `sys_species` | 养殖种类 | —— |
| `sys_pen_type` | 圈舍类型 | —— |
| `sys_animal_status` | 档案状态 | —— |
| `sys_audit_status` | 审核状态 | —— |
| `sys_settle_status` | 结算状态 | —— |
| `sys_mating_type` | 配种方式 | —— |
| `sys_alert_type` | 繁育预警类型 | —— |
| `sys_treatment_status` | 诊疗状态 | —— |
| `sys_material_type` | 物资类型 | —— |
| `sys_vaccine_type` | 疫苗类型 | `{"species":"cattle,sheep"}`（该疫苗适用于哪些畜种） |
| `sys_breed` | 品种 | `{"species":"cattle"}`（该品种属于哪个畜种） |

### 字典如何被业务真正消费（理解它的影响力）
前端通过统一接口 `GET /system/dict/data/query/{dict_type}` 拉取某类型**开启状态**（status=1）的全部数据，直接填充下拉框。两个典型业务：

- **品种下拉**（档案/入栏/配种等几乎所有表单）
  `useSpecies.ts` 调 `/system/dict/data/query/sys_breed`，拿到全部品种后，用 `dict_extra` 里的 `species` 字段**按当前畜种过滤**：
  ```js
  const extra = JSON.parse(d.dict_extra || '{}')   // {"species":"cattle"}
  return !extra.species || extra.species === species.value  // 只有当前畜种的品种才显示
  ```
  → 你新增一个品种，若 dict_extra 写成 `{"species":"sheep"}`，那么在"牛"的档案表单里这个品种就不会出现，只有切到"羊"才可见。

- **疫苗类型下拉**（防疫记录）
  `VaccineListView` 调 `/system/dict/data/query/sys_vaccine_type`，同样按 dict_extra 的 `species`（支持 `"cattle,sheep"` 逗号多畜种）做过滤。

### 操作步骤

**新增一个字典类型**
1. 左栏点「新增」。
2. 填：名称（如「饲料类型」）、类型标识 `dict_type`（如 `sys_material_type_extra`，建议 `sys_` 开头、小写下划线）。
   - 注：**标识若被后端唯一性校验（code 40032）挡住**，说明已有同名标识，换个名。
3. 填状态/备注，保存。
4. 选中新类型（左栏点它），在右栏「新增数据」往里加选项。

**给类型加一条数据（选项）**
1. 在左侧选中目标字典类型。
2. 右栏点「新增数据」。
3. 填：
   - 标签：下拉显示的文本（如「浓缩料」）；
   - 键值：存库的值（可等于标签）；
   - 排序：决定顺序；
   - 扩展信息：如需要按畜种过滤，写 JSON `{"species":"pig"}`，不需要就留空；
   - 状态：正常。
4. 保存 → 该选项立即出现在所有消费这个类型的前端表单里（无需重启、无需刷新缓存）。

> 实测建议：加完一条，前端打开对应业务表单（如档案入栏的"品种"或防疫的"疫苗类型"）即可看到新增项。**实时生效**。

### 避坑要点
- **dict_extra 必须是合法 JSON**：写 `{"species":"cattle"}`（花括号/冒号/引号齐全）。写裸文本会解析失败，下拉按“no species → false”被过滤掉，表现为"这个选项在前端不见了"。
- **停用 vs 删除**：停用某数据，它从下拉消失但数据仍在，可随时恢复；删除则不可逆（软删）。
- **有数据的类型不建议删**：后端 `delete_dict_type` 会检查该类型下是否有数据（code 40034），有则拒绝删除，需先删光该类型的数据。
- **修改会立刻影响表单**：改标签/键值/扩展信息会全局影响所有用到它的下拉；改选项值（dict_value）可能导致历史已存数据与该选项语义不一致，建议只在无业务引用时改。

## 日志管理

> 页面路径：`系统管理 → 日志管理`（路由 `/system/log`）
> 作用：含两个 Tab——**操作日志** 与 **登录日志**，供安全审计、故障排查、用户行为回溯。

### 操作日志（Tab 1）
- 记录**所有写操作**（POST 新增 / PUT 修改 / DELETE 删除），**浏览类 GET 不记录**。
- 每条含：操作人、是否成功、**操作功能（中文）**、业务类型（add/update/delete）、IP、失败信息、操作时间。
- **操作功能列是中文**（如「个体入栏」「审核疫苗记录」「新增公告」），悬停该格可看到背后的原始接口路径，方便排查。
- 支持按操作人账号、按状态（成功/失败）筛选，可清空全部操作日志。
- 每次写请求自动记录，无需人工干预；操作成败以业务返回 `code==200` 为准（业务失败也记 status=失败 + 错误信息）。

### 登录日志(Tab 2)
- 记录每次**登录尝试**：账号、成功/失败、IP、浏览器、操作系统、提示消息、登录时间。
- 用于发现异地登录、暴力破解尝试等安全事件；可按账号 / 状态过滤，支持清空。

> 清空为**删除全部**，操作不可恢复，执行前会弹确认框。

## 通知公告

> 页面路径：`系统管理 → 通知公告`（路由 `/system/notice`）
> 作用：由超管向**指定养殖场**的全体员工发布公告/通知。

### 关键机制（多租户隔离）
- 公告按 `farm_id` **属于某一个养殖场**，只推给**该养殖场**内的活动用户（场主 + 员工）。
- 发布前先在**顶部农场选择器**把当前操作农场切到目标农场，再发公告——公告归属当前选中农场。
- 发布（状态=发布，含由停用改发布）时，自动给该农场每个启用业务用户生成一条**站内消息**（消息列表可看、顶栏铃铛红点提示）。修改已发布公告的其它字段（如标题）**不会重复推送**。

### 操作步骤
1. 顶部农场选择器切到要发公告的养殖场。
2. 点「新增公告」。
3. 填标题、类型（公告 / 通知）、内容、状态（发布 / 停用），保存。
4. 该农场员工的顶栏铃铛会出现红点，点进「我的消息」看到 `【公告】标题` 的消息。

### 其它操作
- 编辑：修改标题/类型/内容/状态（由停用→发布会触发一次推送）。
- 详情：查看某条完整内容。
- 删除：逻辑删除；只影响该公告，已推送的历史站内消息不会撤回。

## 常见问题与避坑

| 现象 | 说明 / 处理 |
| --- | --- |
| **我在菜单管理加了菜单，侧边栏没显示** | 正常。当前侧边栏是 `Sidebar.vue` 硬编码 + 角色 perms 控制，菜单管理是登记/RBAC 台账性质，不驱动侧边栏。见[菜单管理专题](#菜单管理专题详解)。 |
| **改了字典，前端下拉没反应** | 检查：①是否没保存/保存失败；②该项状态是否「停用」（停用不出现在下拉）；③`dict_extra` 是否是合法 JSON（写坏会被按畜种过滤掉）；④当前页面畜种与 dict_extra 的 `species` 是否匹配（品种/疫苗按畜种过滤）。见[字典管理专题](#字典管理专题详解)。 |
| **员工登录看不到某个模块** | 去「用户管理 → 分配角色」，确认该用户角色 `perms` 里包含该模块 key；或给员工换/加一个包含该模块的角色。 |
| **删不掉菜单/角色/字典类型** | 都有级联保护：菜单有子菜单先删子；角色已分配用户不可删；字典类型其下有数据不可删。 |
| **操作日志看不到我浏览页面的记录** | 正常，操作日志只记写请求（增/改/删），浏览类（GET）不入日志。 |
| **发布公告，别人（其他养殖场）也收到了** | 不会。公告严格按当前农场隔离，只推给该农场用户。若觉得串场，检查是否选错农场。 |
